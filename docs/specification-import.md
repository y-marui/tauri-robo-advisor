# Specification: Import and Acquisition

[specification.md](specification.md) の一部。取得方法、表の取り込み、証券会社の出力、bitFlyer・Coincheck・GMO コインの残高を扱う。

## Acquisition Methods

| 対象 | 方式 | 状況 |
|---|---|---|
| 全口座共通 | 手入力（設定タブの「全レコード」で編集） | 基本の方式 |
| 表形式の取り込み | CSV ファイル、または画面の保有一覧をコピーして貼り付けたテキスト（タブ区切り）。取り込むたびに列の対応づけ（名称・評価額・数量など）を画面で指定し、取得元ごとに保存して次回から使う。文字コードは Shift-JIS と UTF-8 を自動判別する | 実装済み（下記） |
| bitFlyer | REST API。API キーは OS のキーチェーンに保存する | 残高取得は実装済み（下記）。証拠金の取得は未実装 |
| Coincheck | REST API。API キーは OS のキーチェーンに保存する | 残高取得は実装済み（下記）。実サービスでの確認は未了 |
| GMO コイン | REST API。API キーは OS のキーチェーンに保存する | 残高取得は実装済み（下記）。実サービスでの確認は未了 |
| ブラウザ拡張 | ログイン済みのブラウザで資産ページを読み取り、ローカルのアプリへ渡す | 将来の選択肢。必要になった時点で設計する |

証券会社ごとの専用パーサーは作らない。会社ごとに形式が違い、版によって変わり、公開された仕様もないため、列の対応づけを利用者が指定する汎用の取り込みにする。例外として、実際のページの構造を確認した**組み込みのレシピ（プリセット）**を、コードではなくデータとして出荷する（[specification-recipes.md](specification-recipes.md) の「Fetch Recipes」）。取り込んだ名称は、商品の別名として保存する。未登録の名称は、利用者が既存の商品へ割り当てるか、新しい商品として登録する。名称の自動推測はしない。

### Table Import

実装は `crates/tabular`（読み取りと列の選択）、`portfolio::plan_import`（別名での対応づけ）、`ReplaceHoldings`（保有の置き換え）。画面の「表の取り込み」カードから使う。

- 入力は、CSV（またはタブ区切り）のファイル、または貼り付けたテキスト。ファイルは UTF-8（BOM の有無を問わない）か Shift-JIS で、どちらでもなければ、文字化けさせずにエラーにする。バイナリ（NUL を含む）も拒否する。区切りは、先頭の数行にタブがあればタブ、なければカンマ。引用符の中の区切り・改行・二重引用符（`""`）を扱う。
- 入力は信頼しない。サイズは 2 MiB、行は 20,000、列は 200、1 つのセルは 1,000 文字までで、超えたら読みの途中でも止める。不正な入力はエラーを返し、パニックしない。読み込んだ表は Rust が 1 つだけ保持し、画面へは先頭 30 行のプレビューだけを返す（表は編集や置き換えのたびに捨てず、読み直すか画面を作り直したときに破棄する）。
- 利用者は、名前の列、評価額の取り方、見出しの行数、1件あたりの行数を指定する。
  - **1件が複数行の表**: 証券会社の保有一覧には、1件の保有が 2 行にまたがるもの（1 行目に名前、2 行目に数量や価格）がある。「1件あたりの行数」（1〜10）と、名前がある行・数値がある行（その中での位置）を指定する。名前と数値は、別の行なら同じ列番号でもよい。
  - **評価額の取り方**: 1 つの列の値、または「数量 × 価格 ÷ 価格の単位」。画面に評価額の列がなく、数量と現在値だけがあるときに使う。このとき、数量と価格は保有に保存する（`quantity`、`price`、`price_unit`）。「評価額の列」を選んだときは、評価額はその列の値を使い、「記録する数量の列」（任意）を選べば、数量も保存する（価格は保存しない）。評価額は、数量 × 価格で計算するか、元の評価額の列を使うかのどちらかで、損益や前日比は扱わない。投信の基準価額は 1 万口あたりなので、単位は 1 または 10,000 から選ぶ。計算は Rust の十進数で行い、桁あふれは範囲外として除外する。外貨の表は、値の通貨に USD を選べば、設定の USD/JPY で円換算される。
  - **1つのセルに複数の値がある表**: 1 つのセルに、複数の値が改行（ページの `<br>`）で、名前ではさらにノーブレークスペースで区切られて入っていることがある（「銘柄コード／銘柄名」、「保有数量／売却可能数量／注文済数量」、「価格／日付」など）。名前・数量（評価額）・価格のそれぞれについて、何番目の値かを指定できる（0 から数える。保存は `name_part` / `value_part` / `price_part`）。指定しないときは、セル全体を読み、改行は空白にする。範囲は 0〜19。数値のセルでは、ノーブレークスペースは桁区切りなので、分けない。ブラウザから読む表でも、セル内の改行とノーブレークスペースは残す（表のタイトルの照合では、空白として扱う）。
  - **前後に文字がある数値**: 「123.45US$」や「150.25（10/15）」のように、数値のまわりに単位や注記がある場合は、「前後の文字を許す」（`loose_numbers`）を選ぶと、セルの中の最初の数値を読む（桁区切り、全角数字、直前の符号を含む）。数値がなければ、これまでと同じく除外する。選ばないときは、セル全体が数値でなければならない。
  - 表の途中の見出しや小計、区分のタイトルの行は、除外した行として理由つきで一覧に出る（先頭の見出しは見出しの行数で飛ばせる）。読めなかった行のあとは、1 行ずつ進めて記録の区切りを探し直すので、途中に 1 行の小計があっても、そのあとの保有は読める。指定は取り込み元の名前ごとに保存し（`SetImportMapping`）、次回から使う。形式が変わったら、列を指定し直すだけでよい。
- 評価額は、桁区切り、円・¥・$ の記号、全角数字、先頭の符号（▲・△ を含む）を読む。数値でない行（小計や見出しなど）、名前のない行、負の値や大きすぎる値の行は、除外して一覧に出す。黙って捨てない。
- 名前は、取り込み元の名前を `source` とする別名で商品に対応づける。自動で推測せず、利用者が選ぶ（bitFlyer と同じ画面部品）。まだ商品がない名前は、その場で商品にできる（`AddProductWithAlias`）: 商品名（既定は取り込んだ名前）、カテゴリ、通貨（既定は取り込みで選んだ通貨。「商品の通貨」のときは円）を選ぶと、商品を作って、同じ操作で別名を結びつける。両方が成功するか、何も変わらないかのどちらかで、商品名が重複しているなどで失敗したときに、作りかけの商品は残らない。カテゴリが 1 つもなければ、先にカテゴリを追加するよう案内する。値の通貨は、既定では対応づけた商品の通貨（商品の設定を優先する）。利用者が通貨を選んだときだけ、別の通貨の商品に対応づけられた名前を除外する。
- **対応づけの手がかり（#131）**: まだ別名のない名前に、同じ名前または似た名前の商品があるとき、`plan_import` が `suggestions`（名前、`exact`、`similar`）として返す。判定は Rust だけで行う。対象は、対応づけられる商品（値の通貨が決まっていればその通貨の商品）。`exact` は、前後の空白を除いて大文字小文字を無視した一致。`similar` は、英数字以外（空白・記号）を除いて小文字にした名前が等しい、または一方がもう一方を含む（短いほうが 2 文字以上）。両方に当てはまる商品がなければ、一致の強いもの（`exact`、等しい、含む）、同じ強さなら商品の並びで先のものを 1 つ選ぶ。画面は、`exact`（なければ `similar`）の商品を「対応づける」の選択で選んでおき（選択肢の先頭にも置く）、行を強調して、その商品の名前を示す情報アイコンを出す。これは手がかりだけで、自動では対応づけない（クリックが必要）。
- 対応づけや商品の作成が拒否されたときは、理由を行の隣にエラー色で示す。同名の商品がある（`conflict: a product with this name exists`）ときは「同じ名前の商品がすでにあります。その商品に対応づけてください。」と読める文にし、その商品を選んでおく。
- 「保有を置き換える」（2 回のクリック）で、選んだ口座の保有を、対応づけ済みの行だけに置き換える。数量と価格は、行にあれば保存する。同じ商品に複数の行（名前）が対応づけられたときは、評価額と数量を合算し、価格はすべて同じときだけ残す（行の価格が違う、または数量のない行があるときは、価格や数量を空にする）。

## bitFlyer Balances

`crates/bitflyer` が `GET /v1/me/getbalance` で残高を取得し、JPY 建ての保有（`rebalance::Holding`）へ変換する。

- API キーには「資産残高を取得」の権限だけを付ける。注文・出金などの権限は不要で、クライアントは `GET` しか送らない。
- 署名は `ACCESS-TIMESTAMP + GET + パス + 本文` の HMAC-SHA256（16 進）。
- 通信は固定の `https://api.bitflyer.com` のみ。リダイレクトは追従せず、タイムアウトと応答サイズの上限を設ける。
- JPY 以外の通貨は、公開 API の `GET /v1/ticker?product_code=<通貨>_JPY` の最終取引価格で評価する（認証情報は送らない）。残高 0 は除く。
- JPY 市場がない通貨（HTTP 400）は評価できないので、`unpriced` として一覧で返す。黙って捨てるとポートフォリオを誤って表示するため。
- 数値は JSON の文字列のまま十進数へ変換し、浮動小数点を通さない。
- API キーとシークレットは OS のキーチェーンにだけ保存し、フロントエンドへは返さない。エラーメッセージや `Debug` 出力にも含めない。
- フロントエンドから呼べるコマンド: `save_bitflyer_credentials`、`has_bitflyer_credentials`、`delete_bitflyer_credentials`、`fetch_bitflyer_holdings`、`fetch_bitflyer_holdings_with_page_prices`、`open_bitflyer_price_page`。

### Prices from the Price Page (#103)

数量は API、価格は公開の価格ページ（`https://bitflyer.com/ja-jp/virtual-currency-chart`、ログイン不要）から取る選択肢。Lightning に円の市場がない通貨（AXS、BAT、BCH、DOT、ETC、LINK、LTC、MANA、MKR、SAND、SHIB、XTZ など）も評価できる。

- **ページの構造**（実ページで 1 回確認）: 表が 1 つ（見出し「通貨ペア」「価格」「前日比」、1 行 1 ペア、`BTC/JPY` と `12,986,322 円`、小さい価格は `0.0007897 円`）。遅延読み込みやタブはなく、約 40 ペアが最初から出る。価格は 1 種類だけ（買値・売値の区別はない）なので、「1 つの価格の基準」はページの価格そのものになる。
- **価格の基準は 1 つ**: 価格ページを選んだときは、すべての通貨をページの価格で評価する（円はそのまま）。評価額 = 数量 × 価格で、数量と価格を保有に記録する（ほかの証券会社と同じ形）。
- **読み方（bitFlyer のカードの中で完結）**: 「価格ページを開く」（`open_bitflyer_price_page`）が、専用ブラウザを起動（最後に使ったもの、なければ最初に見つかったもの。起動済みならそのまま使う）して、固定のアドレス（`bitflyer::PRICE_PAGE_URL`）を新しいタブで開く。同じアドレスのタブがすでにあれば開かない。ブラウザは移動するだけで、入力もクリックもしない（ログインのページを開く操作と同じ扱いで、`login_url_ok` を満たす固定のアドレスだけ。ログインは要らない）。「残高を取得」（`fetch_bitflyer_holdings_with_page_prices`）は、そのタブの表を読み取り専用で読み（`BrowserSession::read_price_page`）、見出しが「通貨ペア」「価格」の表がちょうど 1 つあれば自動で価格として使う（表の選択は要らない）。タブが開いていない・表が見つからない（読み込み前など）ときは、いま何をすればよいか（価格ページを開く、表示されるまで待つ）をエラー文で示す。`<コード>/JPY` で価格が正の行だけ読み、同じ通貨が 2 行あれば断る。アプリ自身はページに接続せず、新しい通信は増えない。
- **評価額の照合**（#100）: 表が評価額と数量と価格をすべて見せるときは、3 つとも読む。評価額が記録の値で、数量と価格は保有に残り、数量 × 価格 ÷ 価格の単位は照合のためだけに使う（`Extracted::computed`、`ImportRow::computed`）。読み取りの指定（`ImportMapping`）は `evaluation_column`（と `evaluation_part`）を価格の列と一緒に持つ。種別の規則の「評価額」は、指定の価格の列（1 株あたり）があれば、価格も記録して照合する。差が通貨の最小単位（円なら 1 円、商品の通貨が分かればその最小単位、分からなければ 1）を超える行は、取り込みの確認の画面（`ImportPlan::differences`）に、名前・読んだ値・計算した値で並ぶ。差があっても取り込みは止めず、評価額を使う。数量か価格がない行、行が短くて価格のセルがない行は照合せず、差としても知らせない。評価額の列は価格の列と一緒にだけ指定でき（数量・価格の列と重ならない）、保存済みの読み取りや、評価額の列のないプリセットはそのまま動く。スキーマ 15。取り込み後の保有の一覧には差を出さない（その場で確かめるもの）。プリセットは 大和コネクト国内株（現在値の列）と楽天の国内株の行が対象。SBI の評価額の列は、実在のページで位置を確かめてから足す。PayPay は数量も価格も出ないので対象外。
- **保存形式**: 価格は保存しないので、レシピやプリセットのスキーマ（版）は変えない。価格の列の位置は `crates/bitflyer` の固定のレイアウト（見出し 2 つ）で、ページが変わったら表を断って知らせる。
- **API の価格との比較**: Lightning の市場がある通貨は、最終取引価格も読み、差（（ページの価格 − API の価格）÷ API の価格、%、小数 2 桁）を参考として返す。意味も更新の時刻も違うので、差はエラーではなく、取り込みも止めない。市場がない・読めない場合は比較が空になる。
- **ページにない通貨**: API の価格があっても、基準が混ざるので評価に使わない。`unpriced` として「価格ページにない」と知らせ、取り込まない。価格がどちらにもない通貨も同じ。
- 画面: 価格の選択（Lightning の最終取引価格 / bitFlyer の価格ページ）。ページを選んだときは、取り込みの結果の上に比較の表（折りたたみ）を出す。

### bitFlyer in the UI

画面の「bitFlyer」カードで、キーの保存・削除と、残高の取り込みを行う。

- キーとシークレットは入力欄（パスワード型）に入れて保存する。保存後は入力欄を空にし、再表示はできない。削除は 2 回のクリックで実行する。「資産残高の取得」の権限だけでキーを作るよう、画面に明記する。
- 残高の取得は、取得してから保有に反映するまで 2 段階にする。取得した通貨は、別名（`source` が `bitflyer`、名前が通貨コード）で商品に対応づける。対応づけは自動で推測せず、利用者が通貨ごとに商品を選び、その選択を別名として記憶する。`portfolio::plan_import`（読み取り専用の `plan_import` コマンド）が、対応づけ済み・未対応・円建てでない商品に対応づけられたもの、に分ける。
- 同じ商品に複数の通貨が対応づけられているときは、その商品の評価額に足し合わせる（商品は 1 行になる）。誤った対応づけは、一覧の「対応づけを外す」で別名を削除（`RemoveAlias`）して、未対応に戻せる。
- 同じ商品が 2 つ作られたときは、記録カードの「統合・分割」で 1 つにまとめる（`MergeProducts { keep, remove, on_conflict }`）。通貨が違う商品は統合できない。カテゴリは残す側のもの。`remove` の別名とレコードは `keep` に移り、`remove` は削除される。同じ口座に両方のレコードがあるときは足さず、`on_conflict`（`keep`: 残す側のレコード、`take`: 消す側のレコード）で選ぶ。別名の上限（50）を超える統合は拒否する。逆に、別名の結びつけを誤ったときは `SplitProduct { product, source, alias, name, accounts }` で、別名を 1 つ新しい商品として切り出す（カテゴリと通貨は元の商品と同じ）。レコードは取り込み元の名前を持たないため、一緒に移すレコードは口座で利用者が選ぶ。買える商品の指定がある口座では、新しい商品も買える。切り出した商品を元の商品に統合すれば元に戻る（`take` で捨てたレコードは戻らない）。
- 多数の商品のカテゴリは、記録カードで選択して一括で設定・変更する（`SetProductsCategory { products, category | new_category }`）。`category`（既存）と `new_category`（名前。同じ編集で作る）はどちらか一方だけ。商品の一覧が空、未知の商品・カテゴリ、両方または両方なし、カテゴリ名の規則違反（空・重複・上限）は拒否し、検証のあとで反映するので一部だけ適用されることはない。新しいカテゴリの目標比率は 0、グループなし。既存カテゴリのグループは変えない。スキーマ変更なし。
- 評価できなかった通貨（`unpriced`）と、円建てでない商品に対応づけられた通貨は、一覧で示して除外する。
- 「保有を置き換える」を押すと（2 回のクリック）、`ReplaceHoldings` の編集で、選んだ口座の保有を、対応づけ済みの残高だけに 1 回の保存で置き換える。その口座にあった、一覧にない保有は消える。数量と価格は、残高にあれば保存する（取引所の残高は数量を持つが、価格は保存しない）。

## Coincheck Balances (#125)

`crates/coincheck` が `GET /api/accounts/balance` で残高を取得し、JPY 建ての保有へ変換する。`crates/bitflyer` と同じ形（`Credentials`、`Transport`、`sign`、`Client`、`Holdings`）で、共通部分の抽出はまだしない。

- API キーには残高を読む権限だけを付ける。第三者の連携サービスの手順は「残高」の権限だけを許可している。公式ページは権限を画面の図でしか示さず、キー作成画面での名称は確認できていない（実サービスで確認したら、ここと画面の案内を直す）。注文・出金などの権限は不要で、クライアントは `GET` しか送らない。IP アドレスでの制限をキーに付けられるので、画面で勧める。
- 署名は `ACCESS-NONCE + URL + 本文` の HMAC-SHA256（16 進）。URL は送るとおりの完全な URL（`https://coincheck.com/api/accounts/balance`）、`GET` の本文は空。ヘッダーは `ACCESS-KEY`、`ACCESS-NONCE`、`ACCESS-SIGNATURE`。
- nonce はミリ秒の時刻で、直前の値より必ず大きくする（時計が戻っても重複しない）。
- 通信は固定の `https://coincheck.com` のみ。リダイレクトは追従せず、タイムアウトと応答サイズの上限を設ける。
- 数量は、通貨ごとの自由な数量に、注文で拘束中の数量（`<通貨>_reserved`）を足したもの（拘束中でも保有である）。貸出（`_lending` など）、借入（`_debt`）、つみたて（`_tsumitate`）は数えない（つみたてが `<通貨>` に含まれるかは公式の記載から確認できていないため、二重に数えないよう外している。実サービスで確認する）。応答が `success: false` のときはエラーにする。
- JPY 以外の通貨は、公開 API の `GET /api/rate/<通貨>_jpy` の販売所レート（`rate`、文字列を十進数として読む）で評価する（認証情報は送らない）。取得した価格は数量と一緒に記録する。残高 0 は除く。JPY の通貨ペアがない通貨（`Invalid pair`: HTTP 400/404、または `success: false`）は、`unpriced` として一覧で返し、保有からは除く。
- 数値は文字列のまま十進数へ変換し、浮動小数点を通さない。
- API キーとシークレットは OS のキーチェーンにだけ保存し（項目名は `coincheck-api-key` / `coincheck-api-secret`）、フロントエンドへは返さない。エラーメッセージや `Debug` 出力にも含めない。
- フロントエンドから呼べるコマンド: `save_coincheck_credentials`、`has_coincheck_credentials`、`delete_coincheck_credentials`、`fetch_coincheck_holdings`。
- 画面は「Coincheck」カード（[ui-design-settings.md](ui-design-settings.md)）。取り込みは bitFlyer と同じ部品（別名の `source` は `coincheck`、名前は通貨コード）で、価格の基準は公開ティッカーの最終価格だけ。

## GMO Coin Balances (#126)

`crates/gmocoin` が `GET /private/v1/account/assets` で残高を取得し、JPY 建ての保有へ変換する。`crates/bitflyer`・`crates/coincheck` と同じ形（`Credentials`、`Transport`、`sign`、`Client`、`Holdings`）で、共通部分の抽出は見送った（[architecture.md](architecture.md) の Extraction Policy の Decision）。

- API キーには資産残高を読む権限だけを付ける。キー作成画面での権限の名称は確認できていない（公式ドキュメントは「機能ごとに指定する」とだけ書く。実サービスで確認したら、ここと画面の案内を直す）。注文・入出金は不要で、クライアントは `GET` しか送らない。IP アドレスでの制限をキーに付けられるので、画面で勧める。
- 署名は `API-TIMESTAMP + メソッド + パス + 本文` の HMAC-SHA256（16 進）。パスは `/v1/account/assets`（URL の `/private` を含めない）、`GET` の本文は空。ヘッダーは `API-KEY`、`API-TIMESTAMP`（ミリ秒の UNIX 時間）、`API-SIGN`。タイムスタンプは GMO コインの時計に近ければよく（ずれると ERR-5008 / 5009）、リクエストをまたぐ単調増加は要求されないので、Coincheck の nonce のような状態は持たない。
- 通信は固定の `https://api.coin.z.com` のみ。リダイレクトは追従せず、タイムアウトと応答サイズの上限を設ける。送るリクエストは署名付きの 1 回だけで、公開 API（ティッカー）は使わない。
- 数量は `amount`（残高。注文で拘束中の分を含む）。`available` は出金予定額を除いた値で、評価には使わない。エラーは HTTP 200 のまま `status` が 0 以外で返る（`messages` の `message_code` と `message_string`）ので、それをエラーにする。メッセージは長さを制限し、制御文字を除く。
- 価格の基準（#126 の決定）: 評価は残高の応答の `conversionRate` を使う。公式ドキュメントでは「販売所での売却価格」で、販売所に取り扱いのない銘柄だけ「取引所現物での最終約定価格」である。利用者が実際に売買する価格が販売所の価格なので、これを他の取引所の販売所レート（Coincheck）と同じ基準として採る。公開の `GET /public/v1/ticker` は、公式ドキュメントに販売所の価格を返すという記載がなく（取引所の現物・レバレッジの銘柄名が並ぶ）、販売所の価格として使えると確認できないため使わない（公開 API を認証なしで叩いて、銘柄名と最終価格の形式だけ確認した）。
- 基準は保有ごとに `basis` で持つ。`sales` は販売所の売値、`board` は取引所の最終約定価格。応答の項目には基準がないため、取引所だけの銘柄（`FCR`・`ASTR`・`NAC`・`WILD`。公式の資産銘柄の表で「取引所」と書かれたもの。2026-10-20 確認）の一覧を `crates/gmocoin/src/client.rs` に 1 か所だけ持ち、それ以外は `sales` とする。銘柄が増えたらこの一覧を更新する。画面は `board` の銘柄を名指しして、混ざっていることを必ず知らせる。
- `conversionRate` が 0 または無い銘柄は `unpriced` として一覧で返し、保有からは除く。残高 0 は除く。
- 数値は文字列のまま十進数へ変換し、浮動小数点を通さない。
- API キーとシークレットは OS のキーチェーンにだけ保存し（項目名は `gmocoin-api-key` / `gmocoin-api-secret`）、フロントエンドへは返さない。エラーメッセージや `Debug` 出力にも含めない。
- フロントエンドから呼べるコマンド: `save_gmocoin_credentials`、`has_gmocoin_credentials`、`delete_gmocoin_credentials`、`fetch_gmocoin_holdings`。
- 画面は「GMO Coin」カード（[ui-design-settings.md](ui-design-settings.md)）。取り込みは Coincheck と同じ部品（別名の `source` は `gmocoin`、名前は銘柄コード）。
