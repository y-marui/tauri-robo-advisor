# Specification

## Status

初期の雛形で、実装済みの機能はない。以下は目指す仕様であり、確定したものから追記する。
実装予定の作業は、このファイルではなく GitHub Issues で管理する。

## Scope

- 日本の証券口座（SBI 証券、楽天証券、マネックス証券、PayPay 証券、bitFlyer など）の資産を集約して表示する。
- 利用者が決めた目標ポートフォリオと比較し、リバランス案を計算して提示する。
- 売買は行わない。提示するだけで、実行は利用者が自分で行う。
- 資産の元データ（Excel など）を取り込まない。商品・口座・目標は、利用者がアプリ内で登録する。

## Data Flow

```
手入力 / 表形式テキストの取り込み / bitFlyer API → 保有（Rust） → リバランス提案（Rust） → UI
```

| 段階 | 内容 |
|---|---|
| 入力 | 手入力を基本とする。取り込みは CSV ファイルまたは貼り付けたテキスト、bitFlyer は REST API で、どれも保有額を上書きする |
| 正規化 | 取得元の名称を、利用者が登録した商品へ対応づけ（別名）、共通の保有モデルへ変換する |
| 計算 | 目標との差から提案を計算する。金額は decimal 型で扱う |
| 表示 | 全体のバランス、保有の一覧、口座ごとの分析と提案を 1 画面に出す |

## Constraints

- 証券会社へのログインはアプリ内で行わない。SBI 証券・マネックス証券はパスキーが必要で、Tauri の組み込み WebView では OS ごとに対応が不完全なため、ログインは利用者がシステムのブラウザで行う。
- ログイン情報（ID・パスワード・パスキー・2FA コード）は扱わず、保存しない。
- bitFlyer の API キー・シークレットは OS のキーチェーンに保存する。
- データはローカルのみに保存し、外部へ送信しない。
- ロジックは Rust 側に置く（[architecture.md](architecture.md) の Layering Policy）。
- 証券会社が出力する形式は変わりうる。取り込みは列の対応づけを利用者が指定する汎用方式にし、形式が変わってもアプリの更新を要しないようにする。
- 個人利用に限る。各証券会社の利用規約を確認して使う。
- 投資助言ではない。

## Rebalance Calculation

`crates/rebalance` の `propose(holdings, targets, params)` が計算する。

- 入力: 保有（銘柄と評価額）、目標配分（銘柄と 0〜1 の比率）、パラメータ（追加投資額 `contribution`、許容乖離 `tolerance`）。
- 基準額: 保有の合計に `contribution` を足した額。銘柄ごとの目標額は「比率 × 基準額」。
- 提案: 目標額と現在額の差を `delta` とし、正なら Buy、負なら Sell。
- 保留: 現在の比率が目標比率から `tolerance` 以内なら Hold（`delta` は 0）。
- 目標にない銘柄は目標比率 0 として扱い、全量売却の提案になる。保有にない銘柄は現在額 0 として扱う。
- 検証: 目標比率の合計は 1（誤差 0.000001 まで許容）、各比率は 0〜1、銘柄の重複・負の金額・負の許容乖離はエラー。
- 金額は十進数で正確に計算し、丸めは行わない。演算はすべて桁あふれを検査し、panic せず `Overflow` エラーを返す（IPC 経由の入力でアプリが異常終了しないため）。丸め（最小売買単位など）は呼び出し側の責務。
- 結果は銘柄名の昇順。

## Acquisition Methods

| 対象 | 方式 | 状況 |
|---|---|---|
| 全口座共通 | 手入力（アプリ内の表で、その場で編集） | 基本の方式 |
| 表形式の取り込み | CSV ファイル、または画面の保有一覧をコピーして貼り付けたテキスト（タブ区切り）。取り込むたびに列の対応づけ（名称・評価額・数量など）を画面で指定し、取得元ごとに保存して次回から使う。文字コードは Shift-JIS と UTF-8 を自動判別する | 実装済み（下記） |
| bitFlyer | REST API。API キーは OS のキーチェーンに保存する | 残高取得は実装済み（下記）。証拠金の取得は未実装 |
| ブラウザ拡張 | ログイン済みのブラウザで資産ページを読み取り、ローカルのアプリへ渡す | 将来の選択肢。必要になった時点で設計する |

証券会社ごとの専用パーサーは作らない。会社ごとに形式が違い、版によって変わり、公開された仕様もないため、列の対応づけを利用者が指定する汎用の取り込みにする。取り込んだ名称は、商品の別名として保存する。未登録の名称は、利用者が既存の商品へ割り当てるか、新しい商品として登録する。名称の自動推測はしない。

### Table Import

実装は `crates/tabular`（読み取りと列の選択）、`portfolio::plan_import`（別名での対応づけ）、`ReplaceHoldings`（保有の置き換え）。画面の「表の取り込み」カードから使う。

- 入力は、CSV（またはタブ区切り）のファイル、または貼り付けたテキスト。ファイルは UTF-8（BOM の有無を問わない）か Shift-JIS で、どちらでもなければ、文字化けさせずにエラーにする。バイナリ（NUL を含む）も拒否する。区切りは、先頭の数行にタブがあればタブ、なければカンマ。引用符の中の区切り・改行・二重引用符（`""`）を扱う。
- 入力は信頼しない。サイズは 2 MiB、行は 20,000、列は 200、1 つのセルは 1,000 文字までで、超えたら読みの途中でも止める。不正な入力はエラーを返し、パニックしない。読み込んだ表は Rust が 1 つだけ保持し、画面へは先頭 30 行のプレビューだけを返す（表は編集や置き換えのたびに捨てず、読み直すか画面を作り直したときに破棄する）。
- 利用者は、名前の列、評価額の取り方、見出しの行数、1件あたりの行数を指定する。
  - **1件が複数行の表**: 証券会社の保有一覧には、1件の保有が 2 行にまたがるもの（1 行目に名前、2 行目に数量や価格）がある。「1件あたりの行数」（1〜10）と、名前がある行・数値がある行（その中での位置）を指定する。名前と数値は、別の行なら同じ列番号でもよい。
  - **評価額の取り方**: 1 つの列の値、または「数量 × 価格 ÷ 価格の単位」。画面に評価額の列がなく、数量と現在値だけがあるときに使う。投信の基準価額は 1 万口あたりなので、単位は 1 または 10,000 から選ぶ。計算は Rust の十進数で行い、桁あふれは範囲外として除外する。外貨の表は、値の通貨に USD を選べば、設定の USD/JPY で円換算される。
  - 表の途中の見出しや小計、区分のタイトルの行は、除外した行として理由つきで一覧に出る（先頭の見出しは見出しの行数で飛ばせる）。読めなかった行のあとは、1 行ずつ進めて記録の区切りを探し直すので、途中に 1 行の小計があっても、そのあとの保有は読める。指定は取り込み元の名前ごとに保存し（`SetImportMapping`）、次回から使う。形式が変わったら、列を指定し直すだけでよい。
- 評価額は、桁区切り、円・¥・$ の記号、全角数字、先頭の符号（▲・△ を含む）を読む。数値でない行（小計や見出しなど）、名前のない行、負の値や大きすぎる値の行は、除外して一覧に出す。黙って捨てない。
- 名前は、取り込み元の名前を `source` とする別名で商品に対応づける。自動で推測せず、利用者が選ぶ（bitFlyer と同じ画面部品）。値の通貨は利用者が選び、別の通貨の商品に対応づけられた名前は除外する。
- 「保有を置き換える」（2 回のクリック）で、選んだ口座の保有を、対応づけ済みの行だけに置き換える。数量は消える。

### Browser Fetch

任意の取得方法（#28）。ブラウザがなくても、ほかの取り込みはすべて使える。`crates/browser` と、画面（「表の取り込み」カードの「ブラウザで取得」）・Tauri のコマンドまで実装済み。

- 対象は Chromium 系の Chrome・Edge・Brave。標準のインストール先から探し、見つからなければ利用者がパスを指定する。chromedriver は要らない。
- アプリは、専用のプロファイルのフォルダ（`--user-data-dir`）でブラウザを起動する。最近の Chromium は既定のフォルダではデバッグのポートを開かず、ポートは全タブとクッキーの操作を許すため、普段使いのプロファイルとは分ける。パスワードマネージャーの拡張はこのプロファイルに入れて、毎回使う。
- ポートは `--remote-debugging-port=0`（空きポート）で、localhost だけ。ポートと接続のパスは、プロファイルの `DevToolsActivePort` から読み、`/devtools/browser/` 以外のパスは受け付けない。
- 同じプロファイルで動作中のブラウザがあれば再利用する。2つ目の起動は動作中のプロセスに引き継がれてすぐ終了するため、成否は終了コードではなくポートへの接続で判断する。
- 専用プロファイルは、ブラウザ自身のプロファイルで、証券会社のサイトが残すもの（端末を信頼するクッキーなど）はブラウザのふつうの動作として残る。アプリはそれを消さず、読まず、保存しない。気になる場合は、ブラウザの設定から消去できる。
- 利用者がブラウザで自分でログインする（パスキーを含む）。セッションはブラウザの終了で切れるので、取得のたびにログインが必要。アプリは、認証情報を読まず、入力せず、保存しない。
- 読み取りは、クレートの中にある固定の 1 つのスクリプトだけ（ページの表を、結合セルを展開した行と文字列にして返す）。呼び出し側から任意の式を渡せる口は公開しない。返ってきた値は形を検査し（表 200、行 5,000、列 200、セル 1,000 文字まで）、合わなければエラーにする。ページの内容をコードとして実行せず、エラーにページの内容を含めない。
- 起動したのに接続できなかったとき（起動が遅い場合を含む）は、アプリが起動したプロセスを止めて、ブラウザを開いたまま残さない。動作中のブラウザへ引き継がれた場合は、止めるものがない。
- **画面の流れ**: ブラウザを選ぶ（見つかったものだけ）→ プロファイルのフォルダ（空ならアプリのデータフォルダの中の `browser-profile`）→ 「ブラウザを開く」→ 利用者がログインして保有一覧のページを開く → ページを選んで「表を取得」→ 保有の表を選んで「この表を使う」→ 以降は、ファイルや貼り付けと同じ列の指定・別名・置き換え。
- **コマンド**: `list_browsers`、`open_browser`（種類とプロファイルのフォルダ。実行ファイルのパスはフロントエンドから受けず、見つかったものから Rust が選ぶ。フォルダは絶対パスで `..` を含まないこと）、`browser_pages`（ホストとタイトルだけを返す）、`fetch_browser_tables`、`use_fetched_table`、`close_browser`。
- 別のプロファイルでもう一度開いたときは、新しいブラウザが立ち上がってから、前のブラウザを閉じる（閉じる手段のないブラウザを残さない）。同じプロファイルなら動作中のブラウザを再利用し、ログインを保つ。
- 取得レシピ（#36）では、読み取りに加えて、通常のリンクをたどって別のページを表示する（上記 Fetch Recipes）。
- 取得が終わったら、アプリが `Browser.close` で専用ブラウザを閉じる（普段使いのブラウザの復元に影響しないように）。

### Fetch Recipes

ログイン後に、ボタン1つで保有の表をまとめて取得する仕組み（#36）。証券会社ごとのコードは持たず、利用者が保存する「レシピ」で動く。

- **レシピ**: 名前、たどるリンク（見える文字。最大 5 つ）、表の先頭のセルの書き出し、値の通貨、更新する口座、列の指定（取り込み元の名前を含む）。リンクには、行き先を表す**参照**を持てる。
- **作り方**: 「表の取り込み」で一度手で取得して列を指定したあと、「レシピとして保存」でリンクの文字と表の書き出しを足す。表の書き出しは、ブラウザで取得した表の先頭のセルの文字が入る。
- **リンクのたどり方**（`crates/browser`、`follow_link`）: 開いているページの `<a>` から、見える文字が完全に一致するものを探し、検査した行き先へ**直接移動する**（リンクを押す動作はしない。押すと、ページがリンクに付けたスクリプトが動くため）。移動の直前に、文字・サイト・行き先（パス・クエリ・`#` 以降）がもう一度一致することを、ページの中で確かめる。
  - たどるのは、同じサイト（スキーム・ホスト・ポートが同じ。`https` のページから `http` のリンクへは行かない）の、実際の行き先（アドレス）を持つ通常のリンクだけ。`javascript:`・`#` やアドレスのないリンクは、押すとページ自身のスクリプトが動き、移動だけだとは言い切れないので、たどらない。ボタン、フォーム、入力欄、スクリプトも扱わない。
  - 文字か行き先が、注文・売買・入出金・振替・解約・変更・更新・保存・編集・登録・削除・送信・ログアウトなどに見えるリンクは、押さない。閲覧を示す言葉があれば許す（文字は「照会」「履歴」「一覧」「余力」「残高」など。行き先は、パスの各区切り（`/` ごと）、クエリの各組（`&` ごと）、`#` 以降（ハッシュで画面を切り替えるページがあるため）を**別々に**判断する。言葉は 2 種類ある。**行為を示す言葉**（キャンセル・削除・送信・保存・変更・更新・編集・登録・解約・購入・売却…）は、閲覧の言葉が同じ部分にあっても許さない（`Cancel order history`、`deletehistory` は断る）。**注文や金額の言葉**（注文・入金・出金・振替・order・transfer・payment…）は、閲覧を示す言葉（照会・履歴・一覧・余力・inquiry・history・list・balance など）が同じ文字・同じ部分にあるときだけ許す。隣の区切りに閲覧の言葉があっても許さない。`edit`・`apply`・`send` は語の先頭にあるときだけ数える（`credit` は問題にしない）。例: 許す =「注文照会」「買付余力」、`/orderhistory/list`。許さない = `/transfer/history`、`/history/delete`、`/transfer?account=1`、`/page?action=cancel`）。判断の前に、`%xx` の符号化を（二重でも）元に戻す（`/trans%66er` は `/transfer`）。実際に移動するアドレスは元のままにする。
  - 同じ文字のリンクは、すべて調べて、行き先ごとに1つにまとめる。行き先が同じなら、複数あっても1つとして押す。行き先が違うときは、勝手に選ばず、利用者に選んでもらう。選んだ行き先は参照として保存する。保存した参照に合うリンクがなければ（ページが変わった）、別のリンクを押さずに止めて、選び直しを求める。
  - 参照として保存するのは、行き先（パスと、変わらないクエリと、`#` 以降）の**指紋**（短いハッシュ。`h:` で始まる 16 桁）だけで、アドレスそのものは保存しない。リンクが運ぶトークンや識別子が、データファイルに入らないようにするため。毎回変わる部分を見落として指紋が合わなくなっても、危険な方向には動かず、「リンクが変わりました」と止まって選び直しになる。選ぶ画面には、そのときだけ行き先の文字を見せる（保存しない）。参照のもとにするのは、行き先のパスと、変わらないクエリと、`#` 以降だけ（`%73ession` のように符号化された名前や値も、元に戻して判断する。`_SeqNo` のようなセッション番号、`session`・`token`・`time` などを含む名前、時刻（13 桁以上の数字）や長いトークン（24 桁以上の 16 進）は落とす。口座番号のような短い数字は、行き先の一部として残す）。行き先が 500 文字を超えるリンクは、検査できないので押さない。URL そのものは保存せず、移動にも使わない。
  - 移動したあとは、新しいページに替わって読み込みが終わるまで（最長約 18 秒）待つ。移動の前に、今のページに印を付けておき、その印が消えた（新しいページに替わった）こと、または、ページを読み込み直さずにアドレスだけが変わるページでは、アドレスが変わったことを確かめる。古いページが「読み込み済み」と答えている間は、先へ進まない。そのあと、ページの内容が一定時間（約 1.5 秒）変わらなくなるまで（最長約 8 秒）待ってから読む。読み込みが遅いページでは、表がまだ前の画面のものである可能性は残る（待ち時間で完全には防げない）。そのため、結果は反映の前に必ず利用者が確認する。どのレシピも、実行が終わる（成功・失敗・選択待ちのいずれでも）と、履歴を戻して開始したページに戻る。次のレシピは、いつも同じ開始ページから始まる。
- **表の選び方**: 先頭のセルがレシピの書き出しで始まる表が、ちょうど 1 つあること。0 または複数ならエラー（書き出しをより具体的にする）。
- **「すべて取得」**: ブラウザを開いて、利用者がログインしたあと、ページを選んで押すと、全レシピを順に実行する。各ページの上のナビゲーションから、どのページからでもたどれる前提。結果（対応づけ済み、未対応、除外した行）をまとめて見せ、未対応の名前は、取り込みと同じ画面で商品に対応づける。
- **反映**: 結果を確認して「口座に反映する」を2回押すと、同じ口座に出す**すべてのレシピ**に結果があることを確かめたうえで（失敗した・選択待ち・あとから足したレシピがあれば、足りないレシピの名前を示して止める。部分的な結果で口座を置き換えると、足りない分の保有が消えるため）、口座ごとに、その口座に出すすべてのレシピの対応づけ済みの行を合算（同じ商品は足す）して、保有を置き換える。**対応づけ済みの行が1つもない口座は、そのままにする**（初回に何も対応づけていなくても、保有が空にならない）。すべての口座を一度に確かめ、一度に保存する。計画を作ってから反映するまでの間にデータ（レシピ・別名・商品など）が変わったときは、反映せずに「もう一度取得」と案内する。
- 読み取った行は Rust が保持し（保有を含むため、反映するか破棄するまで）、フロントエンドへは計画だけを返す。保持した行は、実行したときのレシピと一緒に覚え、そのレシピが変更・削除されたら捨てる（古い口座や通貨で反映しない）。保存したレシピと取り込みの列の指定は、読み込むたびに、保存時と同じ規則（名前の重複なし、50 件まで、列・行・通貨・リンクの範囲）で検査する。計画は、別名の変更のたびに作り直す。

|---|---|---|
| SBI 証券 | 「保有証券」画面の「CSVダウンロード」（PC 版アプリ HYPER SBI 2 は「CSVエクスポート」）があると複数の第三者が報告 | 列の仕様は非公開。10 列と 11 列の版があり、文字コードは Shift-JIS と UTF-8 の両方。表を折りたたんだ状態で出力すると、閉じた部分は含まれない。投資信託や外国株を含むかは未確認 |
| 楽天証券 | 「保有商品一覧」の「すべて」タブの「CSVで保存」（PC のみ） | ファイル名は `assetbalance(all)_日付_時刻.csv` の形式。「国内株式」などのタブで保存した CSV は形式が異なる |
| マネックス証券 | 保有残高の CSV は確認できなかった | 「全取引履歴」の CSV と、銘柄スカウターの CSV（PC のみ）はある |
| PayPay 証券 | 保有銘柄の CSV は確認できなかった | PayPay アプリの取引履歴 CSV（資産運用の売買を含む。直近 2 年、1 回 365 日まで）は保有一覧ではない |

出力できない証券会社は、画面の表をコピーして貼り付けるか、手入力にする。

## bitFlyer Balances

`crates/bitflyer` が `GET /v1/me/getbalance` で残高を取得し、JPY 建ての保有（`rebalance::Holding`）へ変換する。

- API キーには「資産残高を取得」の権限だけを付ける。注文・出金などの権限は不要で、クライアントは `GET` しか送らない。
- 署名は `ACCESS-TIMESTAMP + GET + パス + 本文` の HMAC-SHA256（16 進）。
- 通信は固定の `https://api.bitflyer.com` のみ。リダイレクトは追従せず、タイムアウトと応答サイズの上限を設ける。
- JPY 以外の通貨は、公開 API の `GET /v1/ticker?product_code=<通貨>_JPY` の最終取引価格で評価する（認証情報は送らない）。残高 0 は除く。
- JPY 市場がない通貨（HTTP 400）は評価できないので、`unpriced` として一覧で返す。黙って捨てるとポートフォリオを誤って表示するため。
- 数値は JSON の文字列のまま十進数へ変換し、浮動小数点を通さない。
- API キーとシークレットは OS のキーチェーンにだけ保存し、フロントエンドへは返さない。エラーメッセージや `Debug` 出力にも含めない。
- フロントエンドから呼べるコマンド: `save_bitflyer_credentials`、`has_bitflyer_credentials`、`delete_bitflyer_credentials`、`fetch_bitflyer_holdings`。

### bitFlyer in the UI

画面の「bitFlyer」カードで、キーの保存・削除と、残高の取り込みを行う。

- キーとシークレットは入力欄（パスワード型）に入れて保存する。保存後は入力欄を空にし、再表示はできない。削除は 2 回のクリックで実行する。「資産残高の取得」の権限だけでキーを作るよう、画面に明記する。
- 残高の取得は、取得してから保有に反映するまで 2 段階にする。取得した通貨は、別名（`source` が `bitflyer`、名前が通貨コード）で商品に対応づける。対応づけは自動で推測せず、利用者が通貨ごとに商品を選び、その選択を別名として記憶する。`portfolio::plan_import`（読み取り専用の `plan_import` コマンド）が、対応づけ済み・未対応・円建てでない商品に対応づけられたもの、に分ける。
- 同じ商品に複数の通貨が対応づけられているときは、その商品の評価額に足し合わせる（商品は 1 行になる）。誤った対応づけは、一覧の「対応づけを外す」で別名を削除（`RemoveAlias`）して、未対応に戻せる。
- 評価できなかった通貨（`unpriced`）と、円建てでない商品に対応づけられた通貨は、一覧で示して除外する。
- 「保有を置き換える」を押すと（2 回のクリック）、`ReplaceHoldings` の編集で、選んだ口座の保有を、対応づけ済みの残高だけに 1 回の保存で置き換える。その口座にあった、一覧にない保有は消える。数量は消える。

## Portfolio Model

| 要素 | 内容 |
|---|---|
| カテゴリ | 利用者が名前を決める分類（例: 株式、債券など）。目標比率を持つ。合計は 1 |
| 商品 | 内部 ID と名称を持ち、1 つのカテゴリに属する。通貨（既定は JPY）を持つ。取得元の名称は別名として複数ひも付けられる |
| 口座 | 証券会社などの保有の入れ物。下記の属性を持つ |
| 保有 | 商品 × 口座の評価額（数量があれば数量も） |
| 目標 | カテゴリごとの目標比率。カテゴリごとに「商品は自由」か「商品比率あり」を選ぶ。「商品比率あり」のカテゴリでは、カテゴリ内の商品の相対比率を持つ。商品比率を決めない場合は、等分または現在の比率の維持を選べる |

- カテゴリの目標は必ず持つ。商品の比率は、必要なカテゴリだけ指定する。
- 現金・預金も商品として扱い、どのカテゴリに入れるかを利用者が決める。
- 暗号資産の取引所は、口座（保有の入れ物）として扱う。
- 商品の分類やカテゴリ名、目標比率はすべて利用者のデータで、リポジトリにもアプリの初期データにも含めない。

### Accounts

口座は次の属性を持つ。

- 種別（特定口座、NISA、iDeCo、ポイント、暗号資産、預金など）
- 売却してよいか。NISA などは、既定で売却を提案しない
- その口座で買える商品の一覧
- 追加の原資の種類（現金かポイントか）
- 提案額の丸め単位（既定 1,000 円）

全体リバランスの対象口座は、同時に 1 つだけ選べる（既定は主口座）。売却を提案するのは、対象口座のうち売却してよい口座だけ。それ以外の口座は、買い増しだけを提案する。税金は計算せず、画面に「税金は考慮していません」と明記する。

## Suggestion Modes

画面の全体と、口座ごとのタブに、次の 4 つを出す。

| モード | 内容 |
|---|---|
| 定額追加 | 入力した金額 X を、売らずに配る。目標を最も下回るカテゴリから順に、目標に届くまで足し、全部が届いたら残りを目標比率で按分する。カテゴリの中では、商品比率に同じ考え方を使う |
| 売らずに達成する追加額 | 売却なしで目標に届く最小の総額（各カテゴリの「現在額 ÷ 目標比率」の最大値）と、カテゴリごとの不足額 |
| フル・リバランス | 今の総額のまま、売りと買いで目標に合わせる。売買の対象は全体リバランスの対象口座のみで、ほかの口座の保有額は動かさない前提 |
| 定額売却 | 入力した金額 Y を、目標を最も上回るカテゴリから順に売る。売れるのは売却してよい口座だけ |

- 対象口座に、足りないカテゴリの商品がなくて調整できない場合は、「実行できない」と理由を表示する。
- 許容乖離（これ以内なら提案しない幅）は、カテゴリが 1 ポイント、商品が 0 を既定とし、設定で変えられる。
- 提案額は、口座ごとの丸め単位に丸め、丸めたあとの合計が指定額に合うように、一番大きい項目で調整する。
- 個別株は金額だけを提案する（株数は、株価と単元株数の入力が要るため扱わない）。
- 外貨は、商品に通貨を持たせ、為替は USD/JPY を 1 欄で手入力する。株価と為替の自動取得はしない。

### Calculation Details

実装は `crates/suggest`。評価額はすべて JPY に換算し（JPY と USD のみ対応。USD は手入力のレートで換算）、正確な十進数で計算する。1 兆円を超える金額と、大きすぎる比率は、桁あふれを避けるため受け付けない。

- **水位配分**: 比率が目標を最も下回るものから順に足し、足す額が増えると、次に低いものが加わる。全部が加わると、残りは目標比率で按分される。売らない。カテゴリで配分したあと、カテゴリ内の商品にも同じ方法で配る。
- **商品の目標の持ち方ごとの配り方**: 「比率を指定」は商品の相対比率、「等分」は同じ比率、「現在の比率を維持」は現在額の比率に向けて配る。「自由」は、買えるものに等しく配る。売るときは、「自由」と「現在の比率を維持」は口座の保有額に比例し、ほかは商品の比率で、多すぎるものから売る。
- **売却**: 水位配分の符号を反転した計算で、目標を最も上回るものから売る。1 つの商品について、その口座の保有額を超えて売らない。目標が 0 のカテゴリは、先に売り切る。
- **売らずに達成する追加額**: 各カテゴリの「現在額 ÷ 目標比率」の最大値を目標の総額とし、その差を必要額とする。使う額は、必要額を口座の丸め単位に切り上げた額。口座が買えないカテゴリがあるときは、足りない額を注記する。目標が 0 のカテゴリが価値を持っていると、売らずには達成できないのでエラーにする。
- **フル・リバランス**: 全体リバランスの対象口座だけで行う。許容乖離の内側のカテゴリは動かさない。売りは、売却してよい口座の保有額と、目標を超えた額までに制限し、買いは、口座が買えるカテゴリで、目標までに制限する。売りと買いの総額は、小さいほうに揃え、丸め単位に切り下げる。実現できなかった分は注記する。**カテゴリ内の商品どうしの入れ替え（カテゴリの合計は目標どおりで、商品の構成だけがずれている場合）は、まだ提案しない。**
- **丸め**: 商品ごとの額を口座の丸め単位の倍数にし、合計が指定額（または揃えた総額）にぴったり合うようにする（最大剰余法）。売りでは、保有額を超える丸めをしない。
- 提案は、ポートフォリオを変更せず、保存もしない。提案をブロックする不備（`issues`）が残っているときは、計算せずにエラーにする。

### Account Tabs

口座ごとのタブは、2 段で構成する。

- 上段: 口座内の商品バランス（商品比率に対する現在額と、足りない額・多い額）
- 下段: 全体のカテゴリ目標から見て、この口座の追加額を、この口座で買える商品にどう配るかの提案

主口座以外のサブ口座は、下段が主に使われる。

実装は `suggest::account_balance`（読み取り専用の `get_account_balance` コマンド）と、下段の `suggest_rebalance`。

- 上段の計算は、カテゴリごとに、その口座の保有額の合計を、口座が持つか買える商品（`tradable` の制限を考慮する）に、商品の目標の持ち方に従って配る。「比率を指定」は商品の比率、「等分」は同じ比率で配り、「自由」「現在の比率を維持」は目標を出さない。
- 目標と不足額は、1 円単位に丸める。カテゴリ内の目標の合計がカテゴリの合計に一致するよう、最大剰余法で端数を配る。不足は正、超過は負。
- カテゴリの間でのお金の移動は、この上段では扱わない（提案の役割）。

## Storage

保存と編集は `crates/portfolio`（モデル・検証）と `src-tauri`（ファイル）で実装済み。

- スキーマのバージョンは 2（取り込みの列の指定、`revision`、取得レシピを足したため）。1 のファイルはそのまま読めて、次の保存から 2 になる。新しい版のファイルは、古いアプリが読まずに断るので、知らない項目を黙って消すことがない。
- 保存先は、アプリのデータディレクトリの `portfolio.json`。所有者だけが読める権限（Unix は 0600）で作り、10 MiB を超えるファイルは開かない。
- ID は数値で、再利用しない。古い参照が別のものを指すことがない。
- フロントエンドは `get_portfolio`（現在の状態と、提案をブロックする不備の一覧 `issues`）と、`apply_portfolio_edit`（1 つの編集 `Edit`）のほか、読み取り専用の `get_overview`（カテゴリごとの評価額と現在・目標の比率）、`get_account_balance`（口座内の商品バランス）と `suggest_rebalance`（提案）を使う。検証・ID の採番・保存は Rust が行い、保存に成功してからメモリを更新する。
- 読み込んだファイルは信頼せず、毎回、バージョン・ID の重複・参照・値の範囲を検査する。読めないファイルは、上書きせずにエラーを返し、編集も受け付けない。
- NISA 口座は、作成時に売却を提案しない設定になる。ポイント口座は、原資がポイントになる。


目標、口座、商品、別名、保有、列の対応づけは、アプリのデータディレクトリに JSON ファイルを 1 つ置いて保存する。

- スキーマのバージョンを持つ。
- 書き込みは、一時ファイルを作ってから置き換え、書きかけのファイルを残さない。
- 保有資産は機密情報なので、ログやエラーメッセージに値を出さない。暗号化は OS のディスク暗号化に任せる。API キーだけは、従来どおり OS のキーチェーンに置く。
- 資産の推移の履歴を追加する段階で、SQLite への移行を再検討する。

## Export

他の解析ソフト（表計算や統計ソフトなど）で使えるように、全データを書き出せる。画面の「エクスポート」ボタンで実行する。

- 書き出し先は、ダウンロードフォルダの中の新しいフォルダ `tauri-robo-advisor-export-<日付>-<時刻>`（UTC。同じ秒の 2 回目は `-2`、`-3`…）。既存のフォルダやファイルは上書きしない。場所と名前はアプリが決め、画面から指定することはできない。
- フォルダは所有者だけが読める権限（Unix は 0700、ファイルは 0600）で作る。資産情報を含むので、画面に注意を表示し、README にも書く。
- ファイル: `holdings.csv`（保有 1 行ずつ。商品・口座・カテゴリの情報と、JPY 換算額、全体に占める割合）、`categories.csv`、`products.csv`、`aliases.csv`、`accounts.csv`、`settings.csv`、`portfolio.json`（アプリの形式での全データ）、`README.txt`（列の説明、バージョン、日時）。
- CSV は UTF-8（BOM つき）、改行は CRLF で、Excel でも文字化けしない。金額と比率は、アプリ内の正確な十進数のまま書き、割合は小数 6 桁に丸める。比率は 1 を基準にした小数（0.25 は 25%）。
- JPY への換算ができない値（為替レートが未設定、JPY と USD 以外の通貨）は空欄にする。その値を含む合計と割合も空欄にし、一部だけの合計を出して誤解させない。
- 利用者が入力した名前が `=`、`+`、`-`、`@` で始まると、表計算ソフトが数式として実行しうる。そのため、名前は先頭にアポストロフィを付けたテキストとして書く。
