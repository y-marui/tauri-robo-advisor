# Specification

## Status

初期の雛形で、実装済みの機能はない。以下は目指す仕様であり、確定したものから追記する。
実装予定の作業は、このファイルではなく GitHub Issues で管理する。

## Scope

- 日本の証券口座（SBI 証券、マネックス証券、bitFlyer）の資産を集約して表示する。
- 利用者が決めた目標ポートフォリオと比較し、リバランス案を計算して提示する。
- 売買は行わない。提示するだけで、実行は利用者が自分で行う。

## Data Flow

```
Broker site / API → Acquisition (Rust) → Normalized asset model → Rebalance logic (Rust) → UI
```

| 段階 | 内容 |
|---|---|
| 取得 | SBI 証券・マネックス証券は、利用者がシステムのブラウザでログインして保有一覧のファイル（CSV 等）をダウンロードし、アプリに取り込む。bitFlyer は REST API を使う |
| 正規化 | 各社の取得結果を共通の資産モデルへ変換する |
| 計算 | 目標配分との差から売買案を計算する。金額は decimal 型で扱う |
| 表示 | 結果を一覧で表示する |

## Constraints

- 証券会社へのログインはアプリ内で行わない。SBI 証券・マネックス証券はパスキーが必要で、Tauri の組み込み WebView では OS ごとに対応が不完全なため、ログインは利用者がシステムのブラウザで行う。
- ログイン情報（ID・パスワード・パスキー・2FA コード）は扱わず、保存しない。
- bitFlyer の API キー・シークレットは OS のキーチェーンに保存する。
- データはローカルのみに保存し、外部へ送信しない。
- ロジックは Rust 側に置く（[architecture.md](architecture.md) の Layering Policy）。
- 証券会社の画面構造が変わると取得が壊れる。取得部分は差し替え可能な単位に閉じ込める。
- 個人利用に限る。各証券会社の利用規約を確認して使う。
- 投資助言ではない。

## Rebalance Calculation

`crates/rebalance` の `propose(holdings, targets, params)` が計算する。

- 入力: 保有（銘柄と評価額）、目標配分（銘柄と 0〜1 の比率）、パラメータ（追加投資額 `contribution`、許容乖離 `tolerance`）。
- 基準額: 保有の合計に `contribution` を足した額。銘柄ごとの目標額は「比率 × 基準額」。
- 提案: 目標額と現在額の差を `delta` とし、正なら Buy、負なら Sell。
- 保留: 現在の比率が目標比率から `tolerance` 以内なら Hold（`delta` は 0）。
- 目標にない銘柄は目標比率 0 として扱い、全量売却の提案になる。保有にない銘柄は現在額 0 として扱う。
- 検証: 目標比率の合計は 1（誤差 0.000001 まで許容）、各比率は 0〜1、銘柄の重複・負の金額・負の許容乖離はエラー。
- 金額は十進数で正確に計算し、丸めは行わない。演算はすべて桁あふれを検査し、panic せず `Overflow` エラーを返す（IPC 経由の入力でアプリが異常終了しないため）。丸め（最小売買単位など）は呼び出し側の責務。
- 結果は銘柄名の昇順。

## Acquisition Methods

| 対象 | 方式 | 状況 |
|---|---|---|
| SBI 証券・マネックス証券 | 利用者がブラウザでログインし、保有一覧のファイルをダウンロードして取り込む | 方式は決定。各社が提供するファイルの形式（列・文字コード）は未調査 |
| bitFlyer | REST API。API キーは OS のキーチェーンに保存する | 残高取得は実装済み（下記）。証拠金の取得は未実装 |
| ブラウザ拡張 | ログイン済みのブラウザで資産ページを読み取り、ローカルのアプリへ渡す | 将来の選択肢。必要になった時点で設計する |

取り込み処理は、ファイルを読む部分と、共通の資産モデルへ変換するパーサーを分ける。パーサーは社ごとに独立した Rust のモジュール（Tauri に依存しない）とし、入力ファイルの検証と、想定外の形式でのエラーを明示的に扱う。

## bitFlyer Balances

`crates/bitflyer` が `GET /v1/me/getbalance` で残高を取得し、JPY 建ての保有（`rebalance::Holding`）へ変換する。

- API キーには「資産残高を取得」の権限だけを付ける。注文・出金などの権限は不要で、クライアントは `GET` しか送らない。
- 署名は `ACCESS-TIMESTAMP + GET + パス + 本文` の HMAC-SHA256（16 進）。
- 通信は固定の `https://api.bitflyer.com` のみ。リダイレクトは追従せず、タイムアウトと応答サイズの上限を設ける。
- JPY 以外の通貨は、公開 API の `GET /v1/ticker?product_code=<通貨>_JPY` の最終取引価格で評価する（認証情報は送らない）。残高 0 は除く。
- JPY 市場がない通貨（HTTP 400）は評価できないので、`unpriced` として一覧で返す。黙って捨てるとポートフォリオを誤って表示するため。
- 数値は JSON の文字列のまま十進数へ変換し、浮動小数点を通さない。
- API キーとシークレットは OS のキーチェーンにだけ保存し、フロントエンドへは返さない。エラーメッセージや `Debug` 出力にも含めない。
- フロントエンドから呼べるコマンド: `save_bitflyer_credentials`、`has_bitflyer_credentials`、`delete_bitflyer_credentials`、`fetch_bitflyer_holdings`。
