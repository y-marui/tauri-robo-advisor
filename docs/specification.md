# Specification

## Status

初期の雛形で、実装済みの機能はない。以下は目指す仕様であり、確定したものから追記する。
実装予定の作業は、このファイルではなく GitHub Issues で管理する。

## Scope

- 日本の証券口座（SBI 証券、楽天証券、マネックス証券、PayPay 証券、bitFlyer など）の資産を集約して表示する。
- 利用者が決めた目標ポートフォリオと比較し、リバランス案を計算して提示する。
- 売買は行わない。提示するだけで、実行は利用者が自分で行う。
- 資産の元データ（Excel など）を取り込まない。商品・口座・目標は、利用者がアプリ内で登録する。

## Data Flow

```
手入力 / 表形式テキストの取り込み / bitFlyer API → 保有（Rust） → リバランス提案（Rust） → UI
```

| 段階 | 内容 |
|---|---|
| 入力 | 手入力を基本とする。取り込みは CSV ファイルまたは貼り付けたテキスト、bitFlyer は REST API で、どれも保有額を上書きする |
| 正規化 | 取得元の名称を、利用者が登録した商品へ対応づけ（別名）、共通の保有モデルへ変換する |
| 計算 | 目標との差から提案を計算する。金額は decimal 型で扱う |
| 表示 | 全体のバランス、保有の一覧、口座ごとの分析と提案を 1 画面に出す |

## Constraints

- 証券会社へのログインはアプリ内で行わない。SBI 証券・マネックス証券はパスキーが必要で、Tauri の組み込み WebView では OS ごとに対応が不完全なため、ログインは利用者がシステムのブラウザで行う。
- ログイン情報（ID・パスワード・パスキー・2FA コード）は扱わず、保存しない。
- bitFlyer の API キー・シークレットは OS のキーチェーンに保存する。
- データはローカルのみに保存し、外部へ送信しない。
- ロジックは Rust 側に置く（[architecture.md](architecture.md) の Layering Policy）。
- 証券会社が出力する形式は変わりうる。取り込みは列の対応づけを利用者が指定する汎用方式にし、形式が変わってもアプリの更新を要しないようにする。
- 個人利用に限る。各証券会社の利用規約を確認して使う。
- 投資助言ではない。

## Rebalance Calculation

`crates/rebalance` の `propose(holdings, targets, params)` が計算する。

- 入力: 保有（銘柄と評価額）、目標配分（銘柄と 0〜1 の比率）、パラメータ（追加投資額 `contribution`、許容乖離 `tolerance`）。
- 基準額: 保有の合計に `contribution` を足した額。銘柄ごとの目標額は「比率 × 基準額」。
- 提案: 目標額と現在額の差を `delta` とし、正なら Buy、負なら Sell。
- 保留: 現在の比率が目標比率から `tolerance` 以内なら Hold（`delta` は 0）。
- 目標にない銘柄は目標比率 0 として扱い、全量売却の提案になる。保有にない銘柄は現在額 0 として扱う。
- 検証: 目標比率の合計は 1（誤差 0.000001 まで許容）、各比率は 0〜1、銘柄の重複・負の金額・負の許容乖離はエラー。
- 金額は十進数で正確に計算し、丸めは行わない。演算はすべて桁あふれを検査し、panic せず `Overflow` エラーを返す（IPC 経由の入力でアプリが異常終了しないため）。丸め（最小売買単位など）は呼び出し側の責務。
- 結果は銘柄名の昇順。

## bitFlyer Balances

`crates/bitflyer` が `GET /v1/me/getbalance` で残高を取得し、JPY 建ての保有（`rebalance::Holding`）へ変換する。

- API キーには「資産残高を取得」の権限だけを付ける。注文・出金などの権限は不要で、クライアントは `GET` しか送らない。
- 署名は `ACCESS-TIMESTAMP + GET + パス + 本文` の HMAC-SHA256（16 進）。
- 通信は固定の `https://api.bitflyer.com` のみ。リダイレクトは追従せず、タイムアウトと応答サイズの上限を設ける。
- JPY 以外の通貨は、公開 API の `GET /v1/ticker?product_code=<通貨>_JPY` の最終取引価格で評価する（認証情報は送らない）。残高 0 は除く。
- JPY 市場がない通貨（HTTP 400）は評価できないので、`unpriced` として一覧で返す。黙って捨てるとポートフォリオを誤って表示するため。
- 数値は JSON の文字列のまま十進数へ変換し、浮動小数点を通さない。
- API キーとシークレットは OS のキーチェーンにだけ保存し、フロントエンドへは返さない。エラーメッセージや `Debug` 出力にも含めない。
- フロントエンドから呼べるコマンド: `save_bitflyer_credentials`、`has_bitflyer_credentials`、`delete_bitflyer_credentials`、`fetch_bitflyer_holdings`。

## Portfolio Model

| 要素 | 内容 |
|---|---|
| カテゴリ | 利用者が名前を決める分類（例: 株式、債券など）。目標比率を持つ。合計は 1 |
| 商品 | 内部 ID と名称を持ち、1 つのカテゴリに属する。通貨（既定は JPY）を持つ。取得元の名称は別名として複数ひも付けられる |
| 口座 | 証券会社などの保有の入れ物。下記の属性を持つ |
| 保有 | 商品 × 口座の評価額（数量があれば数量も） |
| 目標 | カテゴリごとの目標比率。カテゴリごとに「商品は自由」か「商品比率あり」を選ぶ。「商品比率あり」のカテゴリでは、カテゴリ内の商品の相対比率を持つ。商品比率を決めない場合は、等分または現在の比率の維持を選べる |

- カテゴリの目標は必ず持つ。商品の比率は、必要なカテゴリだけ指定する。
- 現金・預金も商品として扱い、どのカテゴリに入れるかを利用者が決める。
- 暗号資産の取引所は、口座（保有の入れ物）として扱う。
- 商品の分類やカテゴリ名、目標比率はすべて利用者のデータで、リポジトリにもアプリの初期データにも含めない。

### Accounts

口座は次の属性を持つ。

- 種別（特定口座、NISA、iDeCo、ポイント、暗号資産、預金など）
- 売却してよいか。NISA などは、既定で売却を提案しない
- その口座で買える商品の一覧
- 追加の原資の種類（現金かポイントか）
- 提案額の丸め単位（既定 1,000 円）

全体リバランスの対象口座は、同時に 1 つだけ選べる（既定は主口座）。売却を提案するのは、対象口座のうち売却してよい口座だけ。それ以外の口座は、買い増しだけを提案する。税金は計算せず、画面に「税金は考慮していません」と明記する。

## Suggestion Modes

画面の全体と、口座ごとのタブに、次の 4 つを出す。

| モード | 内容 |
|---|---|
| 定額追加 | 入力した金額 X を、売らずに配る。目標を最も下回るカテゴリから順に、目標に届くまで足し、全部が届いたら残りを目標比率で按分する。カテゴリの中では、商品比率に同じ考え方を使う |
| 売らずに達成する追加額 | 売却なしで目標に届く最小の総額（各カテゴリの「現在額 ÷ 目標比率」の最大値）と、カテゴリごとの不足額 |
| フル・リバランス | 今の総額のまま、売りと買いで目標に合わせる。売買の対象は全体リバランスの対象口座のみで、ほかの口座の保有額は動かさない前提 |
| 定額売却 | 入力した金額 Y を、目標を最も上回るカテゴリから順に売る。売れるのは売却してよい口座だけ |

- 対象口座に、足りないカテゴリの商品がなくて調整できない場合は、「実行できない」と理由を表示する。
- 許容乖離（これ以内なら提案しない幅）は、カテゴリが 1 ポイント、商品が 0 を既定とし、設定で変えられる。
- 提案額は、口座ごとの丸め単位に丸め、丸めたあとの合計が指定額に合うように、一番大きい項目で調整する。
- 個別株は金額だけを提案する（株数は、株価と単元株数の入力が要るため扱わない）。
- 外貨は、商品に通貨を持たせ、為替は USD/JPY を 1 欄で手入力する。株価と為替の自動取得はしない。

### Calculation Details

実装は `crates/suggest`。評価額はすべて JPY に換算し（JPY と USD のみ対応。USD は手入力のレートで換算）、正確な十進数で計算する。1 兆円を超える金額と、大きすぎる比率は、桁あふれを避けるため受け付けない。

- **水位配分**: 比率が目標を最も下回るものから順に足し、足す額が増えると、次に低いものが加わる。全部が加わると、残りは目標比率で按分される。売らない。カテゴリで配分したあと、カテゴリ内の商品にも同じ方法で配る。
- **商品の目標の持ち方ごとの配り方**: 「比率を指定」は商品の相対比率、「等分」は同じ比率、「現在の比率を維持」は現在額の比率に向けて配る。「自由」は、買えるものに等しく配る。売るときは、「自由」と「現在の比率を維持」は口座の保有額に比例し、ほかは商品の比率で、多すぎるものから売る。
- **売却**: 水位配分の符号を反転した計算で、目標を最も上回るものから売る。1 つの商品について、その口座の保有額を超えて売らない。目標が 0 のカテゴリは、先に売り切る。
- **売らずに達成する追加額**: 各カテゴリの「現在額 ÷ 目標比率」の最大値を目標の総額とし、その差を必要額とする。使う額は、必要額を口座の丸め単位に切り上げた額。口座が買えないカテゴリがあるときは、足りない額を注記する。目標が 0 のカテゴリが価値を持っていると、売らずには達成できないのでエラーにする。
- **フル・リバランス**: 全体リバランスの対象口座だけで行う。許容乖離の内側のカテゴリは動かさない。売りは、売却してよい口座の保有額と、目標を超えた額までに制限し、買いは、口座が買えるカテゴリで、目標までに制限する。売りと買いの総額は、小さいほうに揃え、丸め単位に切り下げる。実現できなかった分は注記する。**カテゴリ内の商品どうしの入れ替え（カテゴリの合計は目標どおりで、商品の構成だけがずれている場合）は、まだ提案しない。**
- **丸め**: 商品ごとの額を口座の丸め単位の倍数にし、合計が指定額（または揃えた総額）にぴったり合うようにする（最大剰余法）。売りでは、保有額を超える丸めをしない。
- 提案は、ポートフォリオを変更せず、保存もしない。提案をブロックする不備（`issues`）が残っているときは、計算せずにエラーにする。

### Account Tabs

口座ごとのタブは、2 段で構成する。

- 上段: 口座内の商品バランス（商品比率に対する現在額と、足りない額・多い額）
- 下段: 全体のカテゴリ目標から見て、この口座の追加額を、この口座で買える商品にどう配るかの提案

主口座以外のサブ口座は、下段が主に使われる。

実装は `suggest::account_balance`（読み取り専用の `get_account_balance` コマンド）と、下段の `suggest_rebalance`。

- 上段の計算は、カテゴリごとに、その口座の保有額の合計を、口座が持つか買える商品（`tradable` の制限を考慮する）に、商品の目標の持ち方に従って配る。「比率を指定」は商品の比率、「等分」は同じ比率で配り、「自由」「現在の比率を維持」は目標を出さない。
- 目標と不足額は、1 円単位に丸める。不足は正、超過は負。
- カテゴリの間でのお金の移動は、この上段では扱わない（提案の役割）。

## Storage

保存と編集は `crates/portfolio`（モデル・検証）と `src-tauri`（ファイル）で実装済み。

- 保存先は、アプリのデータディレクトリの `portfolio.json`。所有者だけが読める権限（Unix は 0600）で作り、10 MiB を超えるファイルは開かない。
- ID は数値で、再利用しない。古い参照が別のものを指すことがない。
- フロントエンドは `get_portfolio`（現在の状態と、提案をブロックする不備の一覧 `issues`）と、`apply_portfolio_edit`（1 つの編集 `Edit`）のほか、読み取り専用の `get_overview`（カテゴリごとの評価額と現在・目標の比率）、`get_account_balance`（口座内の商品バランス）と `suggest_rebalance`（提案）を使う。検証・ID の採番・保存は Rust が行い、保存に成功してからメモリを更新する。
- 読み込んだファイルは信頼せず、毎回、バージョン・ID の重複・参照・値の範囲を検査する。読めないファイルは、上書きせずにエラーを返し、編集も受け付けない。
- NISA 口座は、作成時に売却を提案しない設定になる。ポイント口座は、原資がポイントになる。


目標、口座、商品、別名、保有、列の対応づけは、アプリのデータディレクトリに JSON ファイルを 1 つ置いて保存する。

- スキーマのバージョンを持つ。
- 書き込みは、一時ファイルを作ってから置き換え、書きかけのファイルを残さない。
- 保有資産は機密情報なので、ログやエラーメッセージに値を出さない。暗号化は OS のディスク暗号化に任せる。API キーだけは、従来どおり OS のキーチェーンに置く。
- 資産の推移の履歴を追加する段階で、SQLite への移行を再検討する。

## Export

他の解析ソフト（表計算や統計ソフトなど）で使えるように、全データを書き出せる。画面の「エクスポート」ボタンで実行する。

- 書き出し先は、ダウンロードフォルダの中の新しいフォルダ `tauri-robo-advisor-export-<日付>-<時刻>`（UTC。同じ秒の 2 回目は `-2`、`-3`…）。既存のフォルダやファイルは上書きしない。場所と名前はアプリが決め、画面から指定することはできない。
- フォルダは所有者だけが読める権限（Unix は 0700、ファイルは 0600）で作る。資産情報を含むので、画面に注意を表示し、README にも書く。
- ファイル: `holdings.csv`（保有 1 行ずつ。商品・口座・カテゴリの情報と、JPY 換算額、全体に占める割合）、`categories.csv`、`products.csv`、`aliases.csv`、`accounts.csv`、`settings.csv`、`portfolio.json`（アプリの形式での全データ）、`README.txt`（列の説明、バージョン、日時）。
- CSV は UTF-8（BOM つき）、改行は CRLF で、Excel でも文字化けしない。金額と比率は、アプリ内の正確な十進数のまま書き、割合は小数 6 桁に丸める。比率は 1 を基準にした小数（0.25 は 25%）。
- JPY への換算ができない値（為替レートが未設定、JPY と USD 以外の通貨）は空欄にする。その値を含む合計と割合も空欄にし、一部だけの合計を出して誤解させない。
- 利用者が入力した名前が `=`、`+`、`-`、`@` で始まると、表計算ソフトが数式として実行しうる。そのため、名前は先頭にアポストロフィを付けたテキストとして書く。
