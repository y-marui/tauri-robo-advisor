# Specification: Data Model and Storage

[specification.md](specification.md) の一部。ポートフォリオのモデル、保存、エクスポートを扱う。

## Portfolio Model

| 要素 | 内容 |
|---|---|
| グループ | カテゴリの上の分類（主カテゴリ。例: リスク資産、安全資産）。名前だけを持ち、**グループ自身に目標はない**（目標と現在の比率は、属するカテゴリの合計）。追加・名前の変更・削除ができ、削除してもカテゴリは残って「グループなし」になる。名前は重複不可 |
| カテゴリ | 利用者が名前を決める分類（例: 株式、債券など）。目標比率を持つ。合計は 1。0 または 1 つのグループに属する（属さないカテゴリは「グループなし」として、1 つのまとまりで表示する） |
| 商品 | 内部 ID と名称を持ち、1 つのカテゴリに属する。通貨（既定は JPY）を持つ。取得元の名称は別名として複数ひも付けられる |
| 口座 | 証券会社などの保有の入れ物。下記の属性を持つ |
| 保有（記録） | 口座 × 商品の記録。評価額（数量・価格・価格の単位があれば、それも）を持つ。評価額は商品の通貨で持つ |
| 目標 | カテゴリごとの目標比率。カテゴリ内の商品の持ち方は、カテゴリではなく**商品ごと・提案のモードごと**に持つ（下の Product Shares） |

### Product Shares

商品の比率（重み）を、**商品ごと、提案のモード（定額追加、売らずに達成する追加額、フル・リバランス、定額売却）ごとに**持つ（`Portfolio::product_shares`、編集 `SetProductShare`。#153）。比率は、カテゴリの中で商品に配るとき、また配り方が「商品の比率で配る」のときはすべての商品に配るときの、相対比率である（[specification-suggestions.md](specification-suggestions.md) の Calculation Details）。

- 値は 1 つの十進数（`weight`。0 より大きく、10 億以下）。既定は 1 で、設定のない商品は 1 になり、1 は保存しない。以前あった「等分」「現在の比率を維持」の種類はない（等分は比率 1。#153 の後で廃止）。同じカテゴリの商品が、別々の比率を持ってよい。
- 保存先は全口座で共通（口座ごとには持たない）。口座の戦略（`Strategy::Products`）は自分の比率を使うので、ここは見ない。モードどうしは独立で、同期も整合の検査もしない（#152 で検討中）。
- 商品を削除すると設定も消える。統合では、残す商品の設定が残り、統合される商品の設定は捨てる。整合の検査は、商品が実在すること、同じモードと商品の設定が 1 つだけであること、比率 1 を保存していないこと、比率が範囲内であることを見る。
- カテゴリ内の商品の目標が決まっていないという「不備」はなくなった（商品の比率の入力漏れ、商品のないカテゴリは提案を止めない）。

- グループは、カテゴリの表示のための分類で、提案（リバランス）の計算には使わない。提案はこれまでどおりカテゴリと商品で計算する。
- カテゴリの目標は必ず持つ。商品の比率は、必要なカテゴリだけ指定する。
- 現金・預金も商品として扱い、どのカテゴリに入れるかを利用者が決める。現金も口座ごとの記録（通貨ごとの現金の商品）として持つ。
- 全体（全口座）の商品比率は、その商品の記録の比率の合計。口座内の商品バランスは、その口座の記録の比率を使う。取得で保有を置き換えるときは、記録の比率を残し、一覧から消えた商品でも比率がある記録は評価額 0 で残す。
- 暗号資産の取引所は、口座（保有の入れ物）として扱う。
- 商品の分類やカテゴリ名、目標比率はすべて利用者のデータで、リポジトリにもアプリの初期データにも含めない。

### Accounts

口座は、証券会社・銀行・取引所などの入れ物で、種別を持たない。種別は、口座ではなくレコードが持つ（次の「Account types」）。口座は次の属性を持つ。

- 売却してよいか（口座単位の切り替え。レコードの種別の売却可否も合わせて効く。どちらかが不可なら、そのレコードは売らない）。編集はリバランスのタブで行う（`UpdateAccount`）
- その口座の商品ごとの「売買に加えるか」（保存は、加えない商品の一覧 `excluded` と、「すべて」の提案用の `excluded_all` だけ。既定は空 = すべて加える。保存は空でないときだけ。`SetExcluded`。商品の削除・統合・分割に追従する）。旧「買える商品」（`tradable`）はこの一覧に統合した（スキーマ 19）。加えない商品の保有額は、カテゴリの現在額には数える。保有していない商品を新たに買い始めない規則（`held_only`）は別で、この旗とは独立に効く。編集はリバランスのタブで行う
- 口座の戦略（`strategy`。既定は `portfolio` = ポートフォリオの目標に従う。保存は `products` のときだけ）。`products` は、商品と相対比率の一覧（`StrategyItem`: 商品と、手入力の比率。空欄は等分）で、`SetStrategy` で設定する。検証: 商品は 1〜100 件で、実在し、重複せず、比率は 0 より大きく 1,000,000 以下で小数 6 桁まで（十進の計算を正確に保つ）。比率は全商品に付けるか、全商品を空欄にするかのどちらかで、混在は拒否する。商品の削除で一覧から外れ（空になれば `portfolio` に戻る）、統合では比率を合算する。証券会社から読み取らず、手で入力する。除外（`excluded`）はこの一覧の商品にも効く
- 提案額の丸め単位（既定 1 円。口座ごとに変えられる）。編集はリバランスのタブで行う（`UpdateAccount`）
- 口座の並び順（上へ・下へで入れ替える。この順が、タブ・表・選択肢のすべてで使われる。`MoveAccount`。端では何も変わらない）
- 口座・グループ・カテゴリを指定した位置へ 1 回で動かす（ドラッグ操作用。`MoveAccountTo`・`MoveGroupTo`・`MoveCategoryTo` の `index` は動かしたあとの位置で、0 が先頭。範囲外の位置と未知の id は拒否し、同じ位置では何も変わらず、ほかの行の順は保たれる。ほかの編集と同じく元に戻せる）

### Account types

レコード（口座・商品・種別で 1 件）が、保管の種別を持つ（#99）。1 つの口座が、同じ商品を複数の種別で持てる（例: 特定と NISA）。

- 既定の種別（画面の並び順）: 一般、特定、NISA（成長投資枠かつみたて投資枠かを決めていない NISA。識別子 `nisa`）、NISA成長投資枠（`nisa_growth`）、NISAつみたて投資枠（`nisa_tsumitate`）、旧NISA、現金（識別子は `deposit` のまま。表示名だけ「預金」から「現金」に変えた）、暗号資産。アプリに固定で、データには保存しない（表示名は翻訳）。売却を提案してよいかは種別ごとに利用者が切り替えられる（下記）。初期値は、NISA 系の 4 種別が「売らない」（非課税枠を失うため）で、ほかは「売ってよい」。
- 標準の種別の売却可否は、初期値と違うものだけを `Portfolio::type_sellable_overrides`（種別の識別子 → 売却可否）に保存する（スキーマ 23。空なら書かない）。編集は `SetTypeSellable { id, sellable }` で、標準の種別にも追加した種別にも使う（追加した種別は `CustomType::sellable` を書き換える）。初期値と同じにすると上書きは消える。知らない識別子の編集は断り、ファイルの検査も、標準でない識別子や初期値と同じ上書きを持つファイルを断る。
- 利用者が種別を追加できる（手入力・独自のレシピ用。名前と売却可否。`AddAccountType`・`UpdateAccountType`・`RemoveAccountType`）。iDeCo は既定にせず、必要なら追加する。ポイントは種別から外した。追加した種別を削除すると、そのレコードは「未設定」に戻る（同じ口座に同じ商品の未設定のレコードがあれば、そちらにまとめる）。
- レコードの種別は「未設定」でもよい。レコードのカードで、レコードごとに選ぶ（`SetRecordType`。移す先に同じ口座・商品・種別のレコードがあれば断る）。
- 取得（置き換え）は、まだ口座単位。取得した行が種別を持たないときは、その口座の同じ商品のレコードがちょうど 1 件なら、その種別を引き継ぐ（以前の相対比率と同じ扱い）。
- 提案は、売却可の種別のレコードだけを「持っている額」として売却に使う。買いと口座の評価額は、種別に関係しない。同じ（口座, 商品）を複数の種別で持つときの売る順は [specification-suggestions-accounts.md](specification-suggestions-accounts.md) の Selling from Record Types に従う。口座の残高（`get_account_balance`）の商品ごとの行は、現在額を種別ごとに分けた `types`（種別なしの記録、標準の種別の並び、追加した種別の順。NISA 系は最後）も返す。
- 種別を自動で読み取るのは、表の見出しに種別が出るもの（SBI 証券の国内株式・投資信託）だけを予定している（段階 2）。それ以外のページ（マネックス、楽天、大和コネクトなど）は未設定のままで、手で設定する。この制限は画面と文書に書く。
- 旧データの変換（スキーマ 13 から 14）: 口座の種別を、その口座のレコードの種別にする。特定口座は「特定」、NISA は「NISA」（成長・つみたてのどちらか判断できないため、レコードのカードで手で分ける）、預金は「現金」（`deposit`）、暗号資産は「暗号資産」。iDeCo とポイントは、その名前の追加の種別（その種別の口座があるときだけ作る）。その他は未設定。特定口座は、一般と特定を区別できないので「特定」にする（あとから変えられる）。口座の売却可の設定はそのまま残る。NISA の口座で売却可に変えていた場合、NISA のレコードは売らなくなる（安全な側への変更）。

グループとカテゴリの並び順（口座と同じく上へ・下へで入れ替える。`MoveGroup`・`MoveCategory`。順は配列の順で、画面・グラフの色・凡例がこの順に従う。端では何も変わらない。元に戻すには逆向きに動かす）

「すべて」のタブは、全口座をまたいで提案する（全体リバランスの対象口座は持たない）。どの（口座, 商品）の組が提案に加わるかは、口座ごとの「売買に加える」旗（`excluded` の裏返し）で決め、リバランスのタブの商品一覧でチェックを付け外しする（口座のタブは `excluded`、「すべて」は別の一覧 `excluded_all` を使い、互いに影響しない。「すべて」は口座の列つきの 1 つの表。商品は、その口座で保有しているものだけが候補）。売却を提案するのは、売却してよい口座だけで、それ以外の口座は買い増しだけを提案する（口座のタブでは、その口座について全モードを使える）。税金は計算せず、画面に「税金は考慮していません」と明記する。

## Storage

保存と編集は `crates/portfolio`（モデル・検証）と `src-tauri`（ファイル）で実装済み。

- 保存先は、アプリのデータディレクトリの `portfolio.json`。所有者だけが読める権限（Unix は 0600）で作り、10 MiB を超えるファイルは開かない。
- ID は数値で、再利用しない。古い参照が別のものを指すことがない。
- **保存先の選択（#35）**: 保存先のフォルダは設定で選べる。OS が同期するフォルダ（iCloud Drive など）を指せば、複数のコンピューターでデータを共有できる。同期は OS の仕事で、アプリは何も送らない。選んだフォルダは、ローカルのアプリのデータフォルダに置く小さな `data-location.json`（コンピューターごとの設定）に覚える。フォルダは絶対パスで `..` を含まないこと。使えない選択は、ローカルのフォルダに戻す。
  - **移すとき**: 移す先に `portfolio.json` がなければ、今のデータをそこへ複写する。すでにあるときは、利用者の確認のあとにそのファイルをそのまま使う。もとのファイルは、バックアップとしてそのまま残す。ローカルのフォルダへ戻すこともできる。
  - **古い版で上書きしない**: ファイルに `revision`（受け付けた編集の回数）を持つ。編集の前に、ディスクの版が新しければ先にそれを取り込み、保存の直前にもう一度確かめて、その間に新しい版が保存されていたら保存せず、読み込み直したうえで操作をやり直すよう伝える。ディスクの版が自分より古いとき（バックアップの復元など）は、新しい方として上書きする。ウィンドウに戻ったときと `get_portfolio` のたびに、新しい版があれば取り込む。
  - **同期の問題を隠さない**: 同期が作る競合のコピー（`portfolio 2.json` など）と、まだダウンロードされていないファイル（`.portfolio.json.icloud`）は、画面の上に知らせる。読めないファイルは、これまでどおり上書きしない。
  - **フォルダの切り替えと編集の競合（#43）**: データの場所が変わるたびに増える番号 `data.location`（`PortfolioView` の `data`）を持つ。`apply_portfolio_edit` は、画面を描いた表示の `location` を一緒に受け取り、今の番号と違えば、編集を適用せずに断る（フォルダを切り替える間に送られた編集が、ID が 1 から始まる別のデータに当たるのを防ぐ）。フォルダの切り替えは、取得した行（実行結果）も無効にする。
  - 保有資産は機密情報なので、同期するフォルダは利用者が信頼できる場所を選ぶ。ブラウザ取得の専用プロファイルは同期しない（ローカルのまま）。
- フロントエンドは `get_portfolio`（現在の状態と、提案をブロックする不備の一覧 `issues`）と、`apply_portfolio_edit`（1 つの編集 `Edit`）のほか、読み取り専用の `get_overview`（グループごと・カテゴリごと・記録ごと・口座ごとの評価額と比率。グループごとの項目は、グループが 1 つもなければ空で、あれば、グループの順に並べ、グループなしのカテゴリがあるときだけ最後に `group: null` の項目を足す。目標の比率は、属するカテゴリの目標の合計）、`get_account_balance`（口座内の商品バランス）と `suggest_rebalance`（提案）を使う。検証・ID の採番・保存は Rust が行い、保存に成功してからメモリを更新する。
- 読み込んだファイルは信頼せず、毎回、バージョン・ID の重複・参照・値の範囲を検査する。読めないファイルは、上書きせずにエラーを返し、編集も受け付けない。
- 口座は作成時に売却可で、レコードは種別の売却可否（初期値では NISA・旧NISA の種別は売らない）に従う。


目標、口座、商品、別名、保有、列の対応づけは、アプリのデータディレクトリに JSON ファイルを 1 つ置いて保存する。

- スキーマのバージョンを持つ。
- 書き込みは、一時ファイルを作ってから置き換え、書きかけのファイルを残さない。
- 保有資産は機密情報なので、ログやエラーメッセージに値を出さない。暗号化は OS のディスク暗号化に任せる。API キーだけは、従来どおり OS のキーチェーンに置く。
- 資産の推移の履歴を追加する段階で、SQLite への移行を再検討する。

## Export

他の解析ソフト（表計算や統計ソフトなど）で使えるように、全データを書き出せる。画面の「エクスポート」ボタンで実行する。

- 書き出し先は、ダウンロードフォルダの中の新しいフォルダ `tauri-robo-advisor-export-<日付>-<時刻>`（UTC。同じ秒の 2 回目は `-2`、`-3`…）。既存のフォルダやファイルは上書きしない。場所と名前はアプリが決め、画面から指定することはできない。
- フォルダは所有者だけが読める権限（Unix は 0700、ファイルは 0600）で作る。資産情報を含むので、画面に注意を表示し、README にも書く。
- ファイル: `holdings.csv`（記録 1 行ずつ。商品・口座・種別（`account_type`: 既定の種別の id、追加した種別は名前、未設定は空）・カテゴリ・グループの情報と、JPY 換算額、全体に占める割合）、`groups.csv`（グループごとの目標の合計、評価額、割合）、`categories.csv`（グループの列を含む）、`products.csv`、`aliases.csv`、`product_targets.csv`（商品の持ち方。`mode`・商品・カテゴリ・`targeting`・`relative_weight`。等分の商品は行がない）、`accounts.csv`（売買から除く商品は `excluded_product_ids`）、`settings.csv`、`portfolio.json`（アプリの形式での全データ）、`README.txt`（列の説明、バージョン、日時）。
- CSV は UTF-8（BOM つき）、改行は CRLF で、Excel でも文字化けしない。金額と比率は、アプリ内の正確な十進数のまま書き（画面の表示用の丸めはしない）、割合は小数 6 桁に丸める。比率は 1 を基準にした小数（0.25 は 25%）。
- JPY への換算ができない値（為替レートが未設定、JPY と USD 以外の通貨）は空欄にする。その値を含む合計と割合も空欄にし、一部だけの合計を出して誤解させない。
- 利用者が入力した名前が `=`、`+`、`-`、`@` で始まると、表計算ソフトが数式として実行しうる。そのため、名前は先頭にアポストロフィを付けたテキストとして書く。
