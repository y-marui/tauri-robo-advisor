# Changelog

## [Unreleased]

### Added

- Set or change the category of many products at once (#113): `Edit::SetProductsCategory { products, category | new_category }` validates everything first (empty list, unknown product or category, both or neither of category and new name, and the usual category name rules are refused) and then sets the category of all products, optionally creating the category in the same edit (target 0, no group), so it is one save and one undo step. The Records card has a checkbox per product and a bar with select all shown, select none, select the products of a category, and apply (existing or new category). No schema change.
- Reorder accounts, groups, and categories by drag and drop (#111): `Edit::MoveAccountTo`, `MoveGroupTo` and `MoveCategoryTo` move a row to a given place (`index` is the place afterwards; out-of-range index and unknown id are refused, the same place is a no-op, the other rows keep their order). The three lists share one frontend part (`src/sortable.ts`, pointer events on a grip, no dependency): the dragged row is dimmed, a line shows the drop position, Esc cancels, and the moved row is highlighted for a moment (also after the up/down buttons, which stay). The order computation is in `src/reorder.ts` with tests.
- Groups and categories can be reordered with up/down buttons like accounts (#106): `Edit::MoveGroup` and `Edit::MoveCategory` swap with the neighbor (no-op at the ends, unknown id refused). The stored array order is the order, so the chart colors and legend follow it and no schema change is needed. The settings tab now shows the cards in the order groups, categories, accounts, all records.
- The fetch recipes screen has the same browser part as "Fetch in browser" (browser choice, profile folder, Open/Close browser) below "Open the login pages" (#98); it is one shared component (`views/browser-controls.ts`) using the same Tauri commands. The last browser kind (Chrome, Edge, or Brave) and profile folder are kept in a local file (`browser-settings.json` in the app data folder, command `get_browser_settings`; saved when the browser started) and preselected in both places after a restart; a remembered browser that is no longer found falls back to the first one found. They are not stored in the portfolio data file, and the path rules are unchanged. The profile folder was kept in the webview's local storage before; that is replaced.
- Card reading, stage 1 (#76): a recipe can read repeated blocks ("cards") under a heading instead of a table (`Recipe::cards` = `CardSource { heading, item_depth }`, exclusive with the table title; presets can describe it as data). A fixed read-only script (`crates/browser/js/read_cards.js`, isolated world) finds exactly one visible heading that starts with the text, takes the blocks `item_depth` levels below the region after it, and returns one row per card with each text line as a cell, so the existing import mapping, aliases and replace flow are reused. A page cut at a limit (50 headings, 500 items, 20 lines, 1,000 characters) or with no card is refused; no class names, attributes or link targets are used and nothing is clicked. Schema version 12 (an older app refuses the file). No preset uses it yet.
- Card reading, stage 2 (#76): "Fetch with the browser" lists the card lists of the page next to its tables (one candidate per heading, at the first item depth that gives cards; label "N cards × M lines: heading"); choosing one loads one row per card into the import, and "Save as recipe" stores `cards` (heading and item depth) instead of a table title. Running a cards recipe waits (up to 10 s) for the heading and cards and for two equal reads, then goes through the same extract, alias and replace flow as a table (`ReadSource` in `browser_session.rs`).
- PayPay Securities preset (#76, stage 3), `paypay-sec-holdings` (provisional): reads the cards under 保有銘柄 on the page the person opens by hand after logging in (the mini app entry needs a click, which the app does not make; evaluation only: the page shows no quantity or price). Checked once against the structure of the real page with two holdings; "more" and many holdings are not checked. It has no login page address.
- Merge two products and split an alias out (#101): `Edit::MergeProducts` moves the aliases and the records of one product to another of the same currency (different currencies are refused; the category of the kept product wins; where an account holds both, `on_conflict` picks the record that stays) and removes the first; `Edit::SplitProduct` cuts an alias out as a new product with the records of the accounts the person picks (records have no source name). A split is undone by merging the new product back. In the Records card, each product has a "Merge or split" fold. No schema change.

### Fixed

- Records card: a product name is no longer cut off. The name box grows with the name (and shows it whole as a tooltip), and the merge choices are no longer clipped to 11rem by the table-cell rule for selects; the cause was CSS (a fixed width and `td select` max-width), not a shortening of the text.

- The overall balance panel uses the same color for a category in the bars, the doughnut, and the legend: a category of a group takes the color of its group with the same fading, instead of its own position in the list. The "Current" key is a neutral swatch, since the bars have one color per category.
- The bitFlyer balance fetch was checked against the real service with a read-only key (authentication and balances). Currencies without a yen market on Lightning are left out and reported; taking their prices from the public price page is tracked in #103.

- A saved link is recognized again when a session identifier is carried in the path (`/app/list.do;BV_SessionID=...`, as Rakuten Securities does): the volatile `;name=value` path parameters are left out of the destination fingerprint like the volatile query pairs (other path parameters are kept). A link saved before this change is asked for once.
- Fetching again after "The page changed while the recipes were running" no longer fails the same way: the old starting page is forgotten when the batch stops. A tab that already shows the recipe's table (left on the page the links lead to) is read as it is without looking for the links.
- The Rakuten preset `rakuten-all` reads the right columns again: the name cell spans two columns, so the reader pads an empty cell after it, and the units, price, and evaluation are one column to the right (every row was reported as "not a number").
- An edit sent while the data folder is being switched can no longer be applied to the newly adopted data (#43): the data carries a location number (`data.location`) that changes with the folder, `apply_portfolio_edit` takes the number of the view the edit was made from, and Rust refuses it (nothing applied) if it differs. Switching the folder also invalidates fetched rows that were not applied yet. Reloading the file by content hash on every refresh was considered and not done (see `docs/architecture.md`).

### Added

- A mapping can read the rows of a mixed table by kind (#88): `kind_column` names a cell of the name row, and `kind_rules` give each kind either quantity x price / unit (the unit per rule) or the value of a chosen column (the quantity is recorded, no price is kept). A row whose kind matches no rule is left out and reported as "kind not in the rules" (`unknown_kind`). A mapping without them is read as before. Schema version 13; an older app refuses such a file because it would ignore the rules and misvalue some rows.

### Changed

- Holdings tab columns are now price (with the product's currency), quantity, value (the stored value, in the product's currency), value (JPY), and share.
- The rows left out of a fetch are listed with their reasons in the fetch result ("row 2 (not a number)"), as they were in the table import, instead of only a count.
- The oversized docs are split to fit doc-lint (#89), content unchanged: `docs/specification.md` is an index over `docs/specification-{import,browser,recipes,presets,suggestions,data}.md`, `docs/ui-design-settings.md` holds the settings tab, and the long Design Constraints, Tauri Notes, CI commands, licensing and tech stack sections of `AI_CONTEXT.md` moved to `docs/design-constraints.md` (`AI_CONTEXT.md` keeps the rule headlines and a pointer).
- The Rakuten preset `rakuten-all` reads investment trusts (units x price per 10,000 units) and domestic stocks (the evaluation) by the kind cell, and reports rows of any other kind instead of valuing them wrongly. Stocks are covered by tests with made-up pages only; the kind labels are not checked against a real page.

- `make deploy` and `make dmg` sign the app (and the DMG) with a `Developer ID Application` certificate from the keychain when one exists (`TEAM_ID` / `DEVELOPER_NAME` / `SIGN_IDENTITY`, see `.env.example`), so macOS keeps the app's permissions across deploys (#73). With no certificate the app is signed ad-hoc with a message. The signature is verified after the build. New `make bundle-app`.

- Amounts are shown rounded to the smallest unit of their currency (#68): whole yen for JPY, two decimals for USD, ISO 4217 minor units for the other known currencies, as they are for an unknown one; halves round away from zero. It applies to the Holdings tab (records, subtotals), the overall balance, the per-account balance and the suggestions; quantities, unit prices and ratios are not rounded. Display only: calculation, storage, suggestions, shares, edit fields and exports keep the exact values. The rounding is done in Rust (`portfolio::round_for_display`; `PortfolioView::shown_values` and the JPY amounts of the overview, account balance and suggestion responses); the frontend shows the strings it is given.
- Browser reading follow-ups (#39): the fixed page scripts (table read, link search and move, menu click, settle wait) now run in an isolated world (`Page.createIsolatedWorld`), so a page cannot replace `URL`, `querySelectorAll`, or similar built-ins before the app reads it; the world is made again once if the browser reports the context gone. A recipe read now waits (up to 10 s, polling every 0.5 s) until a table with the recipe's title shows up and the same tables are read twice in a row, instead of relying only on the DOM-quiet heuristic (`Cdp::read_tables_until`); the safety rules are unchanged. The refused-word lists gained password, PIN, reissue, reset, unsubscribe, download and upload words (tests use made-up pages). The decision to keep treating 13+ digit and 24+ hex values as per-visit in link fingerprints is recorded and tested. Trying a real SBI page is still open.
- Holdings tab: the table is read-only. Product names, categories, amounts (now with thousands separators and the product's currency) and the category and group names in the heading rows are text, not fields; all of them are edited in the Records card of the Settings tab, which a new "Edit in Records" button above the table (and in the empty state) opens and scrolls to. The table is rebuilt when a name, category or amount changes in Settings. No Rust change.
- Settings tab: the Products card and the Holdings (manual entry) card are replaced by one "Records" card (全レコード), the full view of every product and every record. Each product has a heading row (name, category, currency, delete, add a record) and one row per record (account, weight, quantity and price read-only, amount, delete); a product-name filter and the add-product form are included. Clearing an amount no longer deletes the record (it is refused with a message; type 0 to keep a weight): a record is deleted only with its Delete button. The Holdings tab's table is unchanged for now. No Rust change.
- The window opens at 1280 x 800 (wide enough for the left column and the main area side by side) instead of 800 x 600, and cannot be made smaller than 720 x 520.
- Holdings tab: the rebalance suggestion no longer runs over the right-hand column. The left column keeps only the overall balance; the wide area beside it has sub-tabs, Holdings (the table), Suggestions (the rebalancing account and the overall suggestion) and By account (the balance inside an account and its suggestion), so the suggestion tables have the room they need and long product names wrap in their cell. The chosen sub-tab is remembered and kept across data refreshes. Suggestions are still computed in Rust.
- Presets are referenced, not copied (#66): a recipe made from a preset keeps only the preset id, its account, and the remembered link destinations; its definition (links, menu, heading, table title, mapping, allowed sites) is read from the app's current preset data each time, so an app update updates every preset recipe. It is read-only in the list, can be fetched or removed, and "Detach as a custom recipe" (`DetachPresetRecipe`) turns it into an ordinary recipe with today's definition (for good). A preset id this version does not have is an error of that recipe only (data kept). Recipes without a preset id are ordinary recipes as before (no migration); adding a preset whose copy an older version made turns that copy into a reference in place, and adding the same preset for the same account twice does nothing. The checks (vetted sites, menu-click rules) run on the effective definition; what a recipe can read or click is unchanged. Schema version 10 (an older app refuses the file). The screen reads `PortfolioView::recipes` (effective recipes) instead of `portfolio.recipes`.
- Holdings tab layout (#67): the panels no longer overlap (the left column's cards were wider than their column and ran over the table; they now stay inside it, and a window of about 1000 px or less stacks the panels). A holding is one line: the category select moved from the product cell into the Category column, and the product cell keeps only the name field. The target and the difference columns are removed from the table (the data and the overall balance panel keep them). Long names are clipped with an ellipsis inside their cell.
- Tabs at the top of the window (Holdings / Import / Settings) replace the one long screen (#52). The holdings table uses the full remaining width, the accounts panel sits under the overall balance, and the table can be grouped by category or by account. The import tab starts with a numbered preset flow. A record with only a weight says it has no value yet. A data file of an older version now says how to start a new file. In the fetch recipes card an account can be created on the spot; a fetch can cover everything, one account, one site, or one recipe; a failed recipe names its account and the page to open and can be fetched again, while the recipes that worked are kept. A retry that cannot start (no open page) forgets that recipe's earlier result (`discard_fetch_run`). The overview (`get_overview`) also returns the value of each account, shown in the by-account holdings view.
- The relative weight of a product inside its category now belongs to the record of the product in an account (`Holding::weight`, edit `SetHoldingWeight`), so the same product can have a different weight in each account (#59). The weight of a product over the whole portfolio is the sum of its records' weights; the balance inside an account uses that account's record. An import keeps the weights of the records it replaces, and a record with a weight stays (with nothing held) when the page no longer lists the product. Schema version 8: an older data file is refused and left untouched (nothing converts it). `products.csv` lost its `relative_weight` column; `holdings.csv` gained one. In the Products card the weight is typed per account.
- CI caches the Rust build with `Swatinem/rust-cache` in the lint, test, and build jobs, so dependencies are not recompiled when `Cargo.lock` is unchanged (#62).
- The funding of an account (cash or points) is gone: nothing used it, and it does not matter which a purchase is paid with. The Accounts card, the data, and `accounts.csv` no longer have it. Schema version 7; an older app refuses such a file.
- The account choice of a preset starts on the account that its recipe already has, or on "---" (nothing chosen); the add button needs a real account.
- The rounding unit of a new account now defaults to 1 yen (it was 1,000 yen), since many investment trusts can be bought in 1 yen steps. Existing accounts keep the unit they have, and it can still be changed per account.
- The app identifier is now `y.marui.Robo-Advisor`, in the same form as the Swift apps (`y.marui.<App-Name>`). The data folder (and the default browser profile inside it) moves to `~/Library/Application Support/y.marui.Robo-Advisor` on macOS; a portfolio file or browser profile in the old `dev.marui.robo-advisor` folder is not read any more and has to be moved by hand. The keychain service name for the bitFlyer key is unchanged, so a saved key keeps working.

### Fixed

- The Monex and Rakuten presets read the units and the price per 10,000 units and compute the value as units x price / 10,000, like the SBI investment trust preset, so the units and the price are kept on the holding (before, only the evaluation and the units were). The Rakuten preset therefore covers investment trusts in yen only; a stock row would be valued wrongly.
- The Rakuten all-holdings preset reads values as yen: a name linked to a product in another currency is reported instead of imported (a preset can now state the currency of its page).
- Rakuten Securities preset (#60): the first version read only every other holding, because it treated each holding as two rows while the page shows one visible row per holding (the detail rows are hidden). The preset now reads one row per holding of the page of all holdings.
- Fetching several times in a row failed at random with "The page changed while the recipes were running" on sites that put a session identifier or a changing query in the address (Rakuten Securities). The page a batch started from is now recognised by its scheme, host, port, and path only (the `;` parameters of path segments, the query, and the fragment are not compared); another path, host, or port still stops the batch. Returning to the starting page after a link still checks the whole address.
- The preset list was empty in the Japanese interface: the labels and descriptions of the Monex, Rakuten, and Daiwa Connect presets had no translation, and a missing translation broke the whole list. They are translated, a missing translation now shows the English text, and a test checks every preset text.

### Added

- Monex Securities investment trusts preset (#60): follows 残高照会 from the page after logging in and reads the holdings table (evaluation, with the units held recorded next to it). The table title may now run over the following cells of the first row, so tables that all start with the same heading cell can be told apart.
- Rakuten Securities preset (#60), `rakuten-all`: follows 保有商品一覧-すべて from the top page after logging in and reads the table of all holdings (evaluation, with the units held recorded next to it). It replaces the earlier `rakuten-funds` (the investment trusts page) of this branch: a recipe saved from `rakuten-funds` now shows the error "the preset does not exist in this version of the app" for that recipe only (its data is kept), so delete it and add `rakuten-all` again. Only holdings in yen are covered; the page has no count or visible total, so check the rows shown before applying them. `rakuten-sec.co.jp` is now a vetted site, because its pages are spread over several hosts. PayPay Securities has no preset: it shows holdings as cards, not a table, so those stay manual.
- Tables that hold small tables in their cells can now be read (#60): the page read returns two groups, the tables without other tables in them and the outer tables (whose inner tables hold no tables of their own); a recipe's title is looked for in the first group, and in the outer tables only when nothing in the first group matches, so pages that were readable before are read as before. Deeper nesting is still treated as page layout, and the table limit counts both groups.
- Groups above the categories (#53): a group is a main category with no target of its own (its target and current share are the sums of its categories). Groups can be added, renamed, and removed (removing keeps the categories, which become ungrouped), and a category is put into a group in the Categories card. The overall balance shows a two-ring doughnut (groups inside, categories outside) with the current share and the target next to each name, categories without a group are one "Ungrouped" entry, and the holdings table gets a subtotal row per group. The export gets `groups.csv` and group columns in `holdings.csv` and `categories.csv`. Suggestions are unchanged. Schema version 11; an older app refuses such a file.
- Menu clicks for vetted sites (#54): the Daiwa Connect Securities presets (domestic stocks, cash) now open their page themselves after the login, by clicking the menu entry (国内株式 > 保有銘柄一覧, 資産照会 > 取引余力・預り資産). A recipe link can carry a `menu` group and an expected `heading`; only a script link of a vetted site that is the single match for both texts is clicked, the texts follow the same word rules as any link, the first heading of the page it opens must match or the batch stops, and there is no going back. `connect-sec.co.jp` is a vetted site. Schema 9. An existing saved Daiwa recipe has no menu link; add the preset again and remove the old one.
- Daiwa Connect Securities cash preset (#37): open the page 取引余力・預り資産 after logging in and fetch; the yen balance (金銭残高) is read and linked by name to a yen product. A mapping can now limit the records read from the top of a table (`max_records`), so the valuations and the total that follow the balance are not read. Schema version 6.
- Reorder accounts: up and down buttons in the Accounts card move an account in the list (`MoveAccount`); the order is used by the tabs, the tables, and the choices. At an end nothing changes.
- Edit names and categories in the holdings table: the name of a category (in its heading row), and the name and the category of a product (in its row) can be changed in place; changing the category moves the product to its new group. The same edits existed in the Categories and Products cards further down, which were hard to find.
- Make a product from an unmatched name (#37): in the result of an import, each name that has no product yet has a name field (the imported name), a category, a currency (the one the table was imported in, or another), and one button that creates the product and links the name to it in a single step (`AddProductWithAlias`; both or neither). The recipes card says to add an account first when there is none, and the import says to add a category first when there is none.
- Open the login pages (#37): a button in the recipes card opens the login page of each site that a recipe reads (SBI Securities, Daiwa Connect Securities so far; the addresses are data of the presets) in a new tab of the browser the app opened, unless a tab of that site is already open. The browser only goes to the address: nothing is typed, clicked, or submitted, and the person logs in by hand. Only plain `https://host/...` addresses are opened.
- Daiwa Connect Securities domestic stocks preset (#37): after logging in, open the list of holdings by hand (the site works by form posts and script links, so no link is followed) and fetch; the evaluation column is read and the quantity is recorded. A recipe can now read a heading table and the one-row tables that follow it (`following_tables`, one table per holding), and has a start site (`start_site`): "fetch everything" reads each recipe from the open page of its own site, so several brokerages can be fetched in one go from their own tabs; the start address of each tab is pinned for the batch. Schema version 5. The presets are limited to what the owner holds and can verify: SBI domestic stocks and funds, Monex / Rakuten / PayPay funds, Daiwa Connect domestic stocks.
- Allowed sites for a recipe (#37): a recipe (or a preset, as data) can name sites such as `example.co.jp`, and then it may follow links to the other hosts of that site (a brokerage often spreads its pages over several hosts). Only a site that contains the host the recipe starts on counts, the target must be `https` with no explicit port and within the site (look-alike hosts are refused), the link address is judged by the usual rules, the target site is checked again in the page before the move and on arrival, and a reference to a link on another host includes the host. At most 3 sites; only vetted sites (`portfolio::VETTED_SITES`: `sbisec.co.jp`, `monex.co.jp`) can be named, so a shared domain can never be allowed. The schema version is 4 (it also covers the recipe's all-tables flag). No preset uses it yet: the SBI foreign-currency pages are on another host and are not tables, so they need a different reader.
- Built-in recipes (presets, #37): the app ships recipes as data for pages whose structure was checked. SBI Securities domestic stocks and investment trusts: start from the top page after logging in, follow "保有資産評価", and read every table of the account types (quantity x current price, units x price per 10,000 units). Pick a preset and an account in the recipes card; it becomes an ordinary recipe that can be read, changed, or removed. A recipe can now read every table that starts with its title (`all_tables`) and put their rows together. `AI_CONTEXT.md` now allows shipping presets as data (still no brokerage-specific parsers). Foreign-currency stocks, cash, and Monex are not covered yet.
- Quantity and price of a holding (#37 follow-up): an import of quantity x price now keeps the quantity, the price, and the price unit with the holding (it used to keep only the value), and an import from an evaluation column can record a quantity column. Rows linked to one product are added up (the price is kept only when all rows have the same one). The holdings table shows the quantity and the price, and `holdings.csv` has `price` and `price_unit` columns. The currency of an import now defaults to the product's own currency (an empty currency); choosing one still leaves out products in other currencies. Profit and loss and day-over-day changes are not read or kept. Schema version 3; older files load with defaults, and an older app refuses a version 3 file.
- Reading a cell that holds several values, and numbers with text around them (#37, first step): a table mapping can pick the n-th value of the name, quantity, and price cells (values are separated by line breaks or no-break spaces, like the `<br>` cells of a brokerage page), and can read the first number of a cell such as `123.45US$` or `150.25（10/15）`. The tables read from the browser now keep the line breaks and no-break spaces of a cell; without a part the cell is read as before (line breaks as spaces). New fields have defaults, so saved mappings and recipes load as they were.
- Data folder setting (#35): the portfolio file can live in a folder the OS syncs between computers (for example iCloud Drive). The data is copied there (or an existing file is used after a confirmation), and the old file stays as a backup. The file now has a `revision`; an edit first adopts a newer file from another computer, a save that lost a race is refused, and conflict copies and not-yet-downloaded files are reported. The app sends nothing itself.
- Fetch recipes (#36): save how a table was fetched (links to follow by their visible text, the table's first-cell start, the column mapping, the account) and fetch everything with one button after logging in. The browser crate may now follow plain same-site `<a>` links that only show another page: links that look like orders or money movements are refused, links with the same text and the same destination count as one, different destinations are never guessed (the user picks and the choice is saved as a reference), and a saved link that has vanished stops the run. Recipes that feed one account are merged before its holdings are replaced, and an account with no linked row is left alone.
- `make deploy` can also publish the DMG, like the `swift-*` repositories: `DEPLOY_DMG=true` and `DMG_DEST` in `.env` (`.env.example` added). `DMG_DEST` no longer has a built-in default, so `make dmg` only builds the DMG unless it is set.
- Browser fetch in the table import (#28): choose Chrome, Edge, or Brave, open it with a profile of its own, log in by hand, read the tables of the page, and pick one to go through the same column choice, alias linking, and replace-holdings flow as a file or pasted text. New commands `list_browsers`, `open_browser`, `browser_pages`, `fetch_browser_tables`, `use_fetched_table`, `close_browser`; the browser is closed on request and when the app quits.
- `browser` crate (first step of the optional browser fetch, #28): finds Chrome, Edge, or Brave, starts it with a profile of its own, and reads pages over the DevTools protocol on localhost. The user logs in by hand; nothing is typed, clicked, or stored. New dependencies: `tungstenite` (WebSocket client, without TLS) with `sha1` and `data-encoding`.
- `make deploy` builds the `.app` and installs it into `/Applications/My Tauri` (kept apart from `/Applications` itself, so it never collides with an App Store version), and `make dmg` publishes the DMG to the iCloud `Build/Tauri` folder for `install-my-apps`. Both are macOS only, and the folders can be overridden with `DEPLOY_DIR` and `DMG_DEST`.
- Table import: a record may span several rows (a name row and a row of numbers, as brokerage holdings pages show them), and the value can be quantity x price / price unit (1 or 10,000, for fund prices) computed with exact decimals. Saved mappings from before keep working.
- Generic table import (#9): load a CSV file (UTF-8 or Shift-JIS, detected automatically) or pasted text, choose the name and value columns (saved per source and reused), link names to products through aliases the user confirms, and replace an account's holdings. New `tabular` crate (no brokerage-specific code) and a new dependency, `encoding_rs`; the import result view is shared with the bitFlyer card.
- bitFlyer card: save and delete the API key (never shown again), fetch balances, link each currency to a product through an alias the user confirms, and replace an account's holdings with the linked balances. New `portfolio` pieces: the `ReplaceHoldings` edit and `plan_import` (also the base for the generic import).
- Account tabs panel: one tab per account with the products inside the account compared with their weights (short or over, in yen) and a suggestion for adding to that account. The new read-only `get_account_balance` command supplies the figures from Rust; the suggestion box is now shared with the overall balance panel.
- Holdings panel: holding records grouped by category with subtotal rows (value, share of the total, target, and difference in points), edited in place. `get_overview` now also returns each holding's JPY value and share, and one valuation is fetched per refresh for all panels.
- Overall balance panel: target-vs-current bars and a composition pie in hand-written SVG, the rebalancing-account selector, and the four suggestion modes shown in the app. The new read-only `get_overview` command supplies the values and shares from Rust.
- Full-record export: an Export button writes CSV files (holdings, categories, products, aliases, accounts, settings), the complete data as JSON, and a README into a new owner-only folder in Downloads, for use in other analysis software. Names that could run as spreadsheet formulas are written as text.
- `suggest` crate with the four suggestion modes (fixed add, buy-only to target, full rebalance, fixed sell): water-filling over categories and products, account rules (sellable, tradable products, rounding unit), exact sums after rounding, and the read-only `suggest_rebalance` command.
- Manual entry screen (vanilla TypeScript, English and Japanese): categories, products, accounts, a holdings table, and settings, with every edit validated and saved by Rust. Frontend unit tests run with `npm test`.
- `portfolio` crate with the portfolio model (categories, products, accounts, holdings, targets), validated edits, and integrity checks, plus JSON storage with atomic writes and the `get_portfolio` / `apply_portfolio_edit` commands.
- `bitflyer` crate: read-only bitFlyer API client that signs requests, fetches balances, and values them in JPY from the public ticker; API credentials are stored in the OS keychain and never returned to the frontend.
- `rebalance` crate: portfolio rebalancing calculation with exact decimal arithmetic, and the `propose_rebalance` Tauri command.
- Cargo workspace and a committed `Cargo.lock`; CI and `make` now run cargo with `--locked`.
- Tauri 2 (vanilla TypeScript) scaffold.
- AGPL v3 license, English and Japanese READMEs, and project documentation.
- CI (security scan, lint, test, build), Dependabot, and dev-charter (full) integration.

### Changed

- Removed the scaffold demo (the `greet` command and the sample UI).
- Documented the dashboard design: portfolio model, account roles, four suggestion modes, a generic table import with saved column mappings (instead of per-broker parsers), JSON storage, and the three-panel layout.
- Changed the planned acquisition method for SBI Securities and Monex from in-app WebView login to importing files downloaded from the user's own browser session, because both brokerages require passkeys that embedded WebViews do not reliably support.
- Removed the unused `tauri-plugin-opener` plugin and its `opener:default` permission to reduce the permission surface and dependencies.
- Set a strict Content Security Policy (production `csp` and development `devCsp`) instead of the scaffold default `null`.
- Relicensed from MIT to AGPL v3 (`AGPL-3.0-only`), with contribution terms that allow future commercial licensing.
